# ADR-0002. Доставка контента, хранение прогресса, чтение агентом, проверка форматов

- **Статус:** принято 07.11.2026 (Р-2, Р-3, Р-6, Р-7 из [architecture/README.md](../architecture/README.md#decisions)). Р-1, 4, 5, 8, 9, 10, 11 приняты 07.11.
- **Контекст:** А-1 (сводка для агента за 1–2 вызова), А-2 (контент — файлы), Н-7/Н-8 (MVP на claude.ai, потом своё PWA), [ADR-0001](0001-stack.md).

Ограничения платформы claude.ai, которые решают многое:
- страница может грузить только файлы, опубликованные вместе с ней, или скрипты с разрешённых CDN — с GitHub или другого сайта нельзя;
- база страницы: документ до 256 КиБ, до 25 000 документов, запись в существующий документ от агента требует версии (`if_version`);
- агент читает базу инструментом `ArtifactData`; с параметром `out_dir` документы сохраняются в файлы и **не попадают в контекст**.

---

## Р-2. Как курс-пакет попадает на страницу

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **A. Встроить в HTML при сборке** (предложено) | Пакет → JSON → внутрь единственного HTML-файла | Один файл, одна публикация. Нет загрузки и состояния «пакет не загрузился». Код и контент всегда одной версии | Любая правка контента пересобирает и переиздаёт всю страницу (код тоже). Растёт размер HTML (тексты тестов и теории; сотни КБ — не проблема при лимите 16 МБ) |
| **B. Отдельный JSON рядом со страницей** | Публикуется `index.html` + `pack.json` (`files`), страница делает `fetch("pack.json")` | Правка контента не трогает код — меньше риск сломать интерфейс. Для PWA это естественная схема (статичный файл + кэш) | Нужна загрузка с ожиданием и ошибкой. Две части могут разойтись по версии (новый код + старый пакет). Нужно проверить, как платформа отдаёт `files` (спайк) |
| **C. Пакет в базе** | Агент записывает пункты в базу (`ArtifactData batch`), как в v0 | Не нужно переиздавать страницу | Противоречит А-2: источник истины — файлы, а база становится копией, которую надо синхронизировать пачками по 50 с версиями. Пакет и прогресс перемешаны. При переезде на PWA переносить и контент |
| **D. Страница читает пакет с GitHub** | `fetch` из репозитория | Правка = `git push` | **Невозможно:** платформа блокирует запросы к другим сайтам, а репозиторий приватный (нужен токен в странице) |

**Рекомендация: A.** Для MVP проще всего и без новых рисков. Переход на B — локальная правка `content/load.ts`; его стоит сделать вместе с PWA (E-9), где B естественнее.

## Р-3. Где хранить прогресс сдач

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **A. Та же коллекция `items`, что у v0** (предложено) | v1 читает документы v0, поля каталога (`title`, `group`, `soft`…) у пунктов пакета игнорирует | Переносить нечего. Откат на v0 работает в обе стороны: обе версии видят одни и те же статусы | В документах остаются лишние старые поля (безвредны, их можно вычистить позже одной пачкой) |
| **B. Новая коллекция `progress`** | Одноразовый перенос `status/score/note` из `items`, старое удаляется | Чистая схема с первого дня | Перенос 84 документов (2 пачки) и момент переключения: пока v0 ещё открыт где-то, его отметки уйдут в старую коллекцию. Откат на v0 теряет то, что отмечено в v1 |
| **C. Личное поддерево `data/users/<id>/items`** | Прогресс у каждого зрителя свой | Готово к общей странице на группу | Общая страница отклонена (каждый — своя копия). Агент от имени владельца читает это поддерево — работает, но лишняя сложность без пользы |

**Рекомендация: A,** плюс необязательная чистка старых полей после того, как v1 проработает неделю.

## Р-6. Как агент читает прогресс в начале сессии

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **A. Выгрузка в файлы + скрипт сравнения** (предложено) | `ArtifactData list items` с `out_dir` (в контекст не попадает) → `tools/agent/diff.ts` сравнивает с прошлым снимком и пакетом → отчёт ≤ 40 строк | В контекст идёт только короткий отчёт. Видны все виды изменений, включая удаления и сирот. Логика в тестируемом скрипте, страница ничего лишнего не пишет | Нужен скрипт и файл прошлого снимка (`private/last-seen.json`). Два шага вместо одного |
| **B. Документ-сводка, который ведёт страница** | При каждом действии страница пересчитывает `meta/summary` | Агенту — одно чтение одного документа | Каждое нажатие = две записи. Несколько открытых вкладок перезаписывают сводку друг другу. «Что изменилось с прошлой сессии» страница сама не знает — нужна отметка «агент прочитал», ещё запись. Логика сводки в коде страницы, который сложнее тестировать |
| **C. Запрос «изменённое после даты»** | `query items where updatedAt > <последняя проверка>` | Одно короткое чтение, без скрипта | Не видит удалений (удалённый свой пункт просто пропадает). Документы идут в контекст целиком. Сирот и правки сроков надо искать глазами |

**Рекомендация: A.** Главный аргумент — расход контекста: при 84+ пунктах выгрузка целиком стоит порядка 5–10 тыс. токенов каждую сессию (оценка, не замер), а отчёт скрипта — около 0,5 тыс. C годится как быстрый способ «глянуть», если скрипт недоступен.

## Р-7. Чем проверять форматы данных

Проверяется: пакет при сборке (YAML → JSON), документы базы при чтении (их мог записать v0, агент или старая версия страницы), позже — экспорт/импорт при переезде на PWA.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. zod** (предложено) | Одна запись — и тип TS, и проверка. Самая распространённая библиотека, лучше всех знакома агентам. Понятные сообщения об ошибках с путём поля | Самая тяжёлая из подходящих: ~15 КБ в сжатом виде (неважно для одного HTML, чуть важнее для PWA) |
| **B. valibot** | Тот же подход, что у zod, но ~1–3 КБ (подключается только используемое) | Меньше примеров, агенты знают хуже — больше ошибок при правках. Немного многословнее |
| **C. JSON Schema + ajv** | Схема — данные: её могут прочитать инструменты на других языках (например, скрипт Anki на Python) | Типы TS придётся генерировать или писать отдельно — два источника, которые расходятся. ajv тяжелее zod. Схемы читать труднее |
| **D. TypeBox** | JSON Schema и тип TS из одной записи; быстрые проверки | Менее известен. Сообщения об ошибках хуже. Для нас выгода JSON Schema пока теоретическая |
| **E. Только типы TS + ручные проверки** | Без зависимостей | Типы и проверки пишутся дважды и расходятся — ровно та ошибка, от которой защищаемся (Т-4 в ADR-0001) |

**Рекомендация: A (zod).** Вес не важен для одного HTML, а знакомость агентам и один источник типов важны. Запасной вариант — B, если размер станет важен в PWA; замена механическая, схемы похожи.

## Решение

- **Р-2 = A** на этапе claude.ai. Требование пользователя к целевому приложению: обновление одним файлом (APK) через Telegram «Избранное».
- **Р-3 = A** на этапе claude.ai (база синхронизируется сама — проще любого обмена). В целевом приложении — локальное хранение и обмен файлом прогресса через «Поделиться» в Telegram (агент забирает его `tg media me …`).
- **Р-6 = A.**
- **Р-7 = A** (zod).

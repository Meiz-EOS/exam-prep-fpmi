## cpp-c-0301 · cpp-t-031
Чем `const` отличается от `constexpr` у переменной?
---
`const` запрещает менять объект после инициализации, но значение может быть известно только в runtime. `constexpr` (подразумевает `const`) требует литерального типа и инициализатора, являющегося constant expression, — значение вычисляется при компиляции и годится для размера массива, `static_assert`, нетипового параметра шаблона.
```cpp
int n = 5;
const int a = n;      // ок, но не constant expression
constexpr int b = n;  // ошибка: n не константа
```
Подвох: `const` целочисленного типа с константным инициализатором тоже годится в constant expression, а `const double` — нет, `constexpr double` — да.
См.: language/constexpr, language/constant_expression

## cpp-c-0302 · cpp-t-031
Что означает `constexpr` у функции?
---
Функцию можно вызывать в constant expression (при константных аргументах); она неявно `inline`. До C++14 тело — один `return`; с C++14 допустимы `if`, `for`, `while`, локальные переменные (с инициализацией, литерального типа), но (в C++14/17) не `goto`, не `try`-блоки, не `static`/`thread_local` переменные; с C++20 разрешены `try`-блоки, с C++23 ограничения ещё смягчены.
```cpp
constexpr int sq(int x) { return x * x; }
constexpr int a = sq(4);  // при компиляции
int n = 5; int b = sq(n); // обычный вызов в runtime
```
Подвох: `constexpr`-функция не обязана вычисляться при компиляции; обязательно — только у `consteval` (C++20).
См.: language/constexpr, language/consteval

## cpp-c-0331 · cpp-t-031
Чем `if constexpr` отличается от обычного `if`?
---
Условие `if constexpr` (C++17) — constant expression, выбор ветки происходит при компиляции; в шаблоне невыбранная ветка отбрасывается и не инстанцируется, поэтому в ней может быть код, некорректный для данного типа. При обычном `if` обе ветки должны компилироваться.
```cpp
template<class T> auto f(T x) {
  if constexpr (std::is_pointer_v<T>) return *x;
  else return x;
}
```
Подвох: вне шаблона отбрасываемая ветка всё равно проверяется компилятором.
См.: language/constexpr, language/constant_expression

## cpp-c-0303 · cpp-t-032
Чем предупреждение компилятора отличается от ошибки?
---
Ошибка — нарушение правил языка (ill-formed программа): компилятор обязан выдать диагностику, результат сборки не получается. Предупреждение — необязательная диагностика подозрительного, но формально допустимого кода; программа собирается.
```cpp
int f() { int x = 0; if (x = 1) return x; } // warning: присваивание в условии, нет return
```
Подвох: UB (например, достижение конца функции без `return`) часто даёт лишь предупреждение или не диагностируется вовсе.
См.: language/ub

## cpp-c-0304 · cpp-t-032
Что делают параметры GCC `-Wall`, `-Wextra` и `-Werror`?
---
`-Wall` включает основной набор предупреждений, `-Wextra` добавляет ещё группу, `-Werror` превращает все включённые предупреждения в ошибки. Типичная строка: `g++ -std=c++20 -Wall -Wextra -Werror a.cpp`.
Подвох: `-Wall` включает не все возможные предупреждения; набор меняется между версиями GCC, поэтому `-Werror` может ломать сборку после обновления компилятора. [не по cppreference]
См.: language/ub

## cpp-c-0332 · cpp-t-032
Чем неопределённое поведение (UB) отличается от неуточняемого (unspecified)?
---
Unspecified: результат — один из допустимых вариантов, программа остаётся корректной (например, порядок вычисления аргументов функции или операндов `+`). UB: никаких ограничений на поведение, компилятор вправе считать, что UB не происходит.
```cpp
z(a(), b(), c()); // unspecified: любой порядок a, b, c
int i = 0;
i = i++ + i;      // UB: неупорядоченные побочный эффект и чтение
```
Подвох: приоритет и ассоциативность задают разбор `a() + b() + c()`, но не порядок вызовов.
См.: language/ub, language/eval_order

## cpp-c-0305 · cpp-t-033
Для чего служит анонимное пространство имён в файле?
---
Члены unnamed namespace имеют внутреннее связывание и доступны от точки объявления до конца единицы трансляции. Так прячут вспомогательные функции и переменные файла, не конфликтуя с одноимёнными сущностями в других `.cpp`.
```cpp
namespace { int counter = 0; } // виден только в этом TU
```
Подвох: из другой единицы трансляции к таким членам не обратиться; анонимное пространство — не то же самое, что глобальное (`::x`).
См.: language/namespace

## cpp-c-0306 · cpp-t-033
Что делает директива `using namespace N;`?
---
using-directive: для неквалифицированного поиска все имена из `N` видны так, будто объявлены в ближайшем объемлющем пространстве, содержащем и `N`, и директиву. Три вида: using-directive, using-declaration `using N::x;` и псевдоним `namespace A = N;`.
```cpp
namespace N { int x = 1; }
using namespace N;
int y = x; // ок
```
Подвох: если такое же имя видно ещё откуда-то на том же уровне, неквалифицированное обращение неоднозначно; using-declaration вводит только одно имя.
См.: language/namespace, language/using_declaration

## cpp-c-0333 · cpp-t-033
Как обратиться к глобальному имени, если его скрывает локальное? Что такое qualified-id?
---
Использовать `::` без левой части: `::x` ищет только в глобальном пространстве. Qualified-id содержит `::` (`N::x`, `::x`), unqualified-id — просто имя `x`: ищется от внутренней области к внешним, останавливаясь на первом найденном объявлении (ближайшее скрывает дальнее).
```cpp
int x = 1;
void f() { int x = 2; int y = ::x; } // y == 1
```
Подвох: слева от `::` ищутся только пространства, классы, перечисления и шаблоны типов — одноимённая переменная игнорируется (`int A; A::n` корректно).
См.: language/qualified_lookup, language/unqualified_lookup

## cpp-c-0307 · cpp-t-034
Чем `new` отличается от `malloc`?
---
`new`-выражение выделяет память и затем создаёт объект (вызывает конструктор), возвращает типизированный указатель. `malloc` лишь выделяет сырую память (`void*`), `calloc` — с обнулением; конструктор не вызывается.
```cpp
std::string* s = new std::string("hi"); // объект создан
void* raw = std::malloc(sizeof(std::string)); // только байты
```
Подвох: освобождение парное: `new` — `delete`, `new[]` — `delete[]`, `malloc` — `free`; `delete` ещё вызывает деструктор перед освобождением, `free` — нет.
См.: language/new, language/delete, memory/c

## cpp-c-0308 · cpp-t-034
Почему `new[]` нужно освобождать через `delete[]`?
---
`delete[]` вызывает деструкторы всех элементов (от последнего к первому) и затем `operator delete[]`. Указатель должен быть получен из `new[]`; `delete` для массива и `delete[]` для одиночного объекта — UB.
```cpp
int* a = new int[3];
delete[] a; // а не delete a
```
Подвох: откуда `delete[]` знает число элементов — стандартом не раскрыто; реализации обычно хранят его в служебном поле перед блоком. [не по cppreference]
См.: language/delete, language/new

## cpp-c-0334 · cpp-t-034
Что такое указатель на функцию и как он работает при перегрузках?
---
Указатель на функцию хранит адрес функции заданной сигнатуры и вызывается как функция. Если имя перегружено, нужная перегрузка выбирается по типу цели (инициализируемого указателя, аргумента, `static_cast`), а не по аргументам вызова.
```cpp
int f(int); int f(double);
int (*p)(double) = f; // выбрана f(double)
int r = p(1.5);
```
Подвох: без целевого типа (`auto p = f;`) выбрать перегрузку нельзя — ошибка; `int *p(double)` — объявление функции, возвращающей `int*`.
См.: language/pointer, language/overloaded_address

## cpp-c-0309 · cpp-t-035
Для чего предназначен `reinterpret_cast`?
---
Переинтерпретирует битовое представление: указатель в указатель другого типа, указатель в целое достаточной ширины (`std::uintptr_t`) и обратно. Значение указателя при этом не меняется (если выравнивание цели не строже); `const` снять нельзя.
```cpp
int x = 1;
auto u = reinterpret_cast<std::uintptr_t>(&x);
int* p = reinterpret_cast<int*>(u);        // ок: тот же адрес
float f = *reinterpret_cast<float*>(&x);   // ошибка: не type-accessible
```
Подвох: разыменовать результат безопасно, только если объект type-accessible (`char`, `unsigned char`, `std::byte`, тот же или знаково-беззнаковый тип).
См.: language/reinterpret_cast

## cpp-c-0310 · cpp-t-035
Когда корректно применять `const_cast`?
---
`const_cast` добавляет или снимает `const`/`volatile` у указателя или ссылки на тот же тип; только он может снять константность. Корректно, если объект на самом деле не `const`; изменение объекта, объявленного `const`, — UB.
```cpp
int v = 1;
const int& r = v;
const_cast<int&>(r) = 2;      // ок: v не const
const int c = 1;
*const_cast<int*>(&c) = 2;    // ошибка: UB, c const
```
Подвох: к указателям на функции и на функции-члены `const_cast` не применим.
См.: language/const_cast, language/explicit_cast

## cpp-c-0311 · cpp-t-036
Что такое агрегатная инициализация?
---
Агрегат (массив или класс без user-declared конструкторов, без private/protected нестатических полей, без виртуальных функций, виртуальных и private/protected баз) инициализируется списком значений для элементов в порядке объявления. Остальные элементы берут default member initializer, иначе инициализируются из пустого `{}`.
```cpp
struct S { int a, b; };
S s{1};        // a == 1, b == 0
S t{1.5, 2};   // ошибка: сужающее преобразование
```
Подвох: лишний инициализатор — ошибка; сужающие преобразования запрещены с C++11.
См.: language/aggregate_initialization

## cpp-c-0312 · cpp-t-036
Какое ограничение есть у designated initializers в C++20?
---
Обозначение должно называть прямое нестатическое поле агрегата, обозначения идут в порядке объявления полей. Запрещены (в отличие от C): другой порядок, вложенные `.a.b`, индексы массивов, смешивание с обычными инициализаторами.
```cpp
struct A { int x, y, z; };
A a{.x = 1, .z = 2}; // ок, y == 0
A b{.y = 2, .x = 1}; // ошибка: порядок
```
Подвох: у `union` допускается только один инициализатор.
См.: language/aggregate_initialization

## cpp-c-0340 · cpp-t-036
Как порядок полей влияет на размер структуры?
---
Нестатические поля с одинаковым доступом размещаются в порядке объявления; между ними и после последнего компилятор вставляет padding для выравнивания, поэтому перестановка полей меняет `sizeof`.
```cpp
struct A { char a; int b; char c; }; // обычно 12
struct B { int b; char a, c; };      // обычно 8
```
Подвох: конкретные размеры зависят от платформы и ABI (здесь типично для x86-64); стандарт лишь допускает padding.
См.: language/data_members

## cpp-c-0341 · cpp-t-036
Как обратиться к внутреннему (nested) классу извне и какой у него доступ к внешнему?
---
Имя вложенного класса лежит в области внешнего: `Outer::Inner`. Вложенный класс видит все имена внешнего (даже private), но не имеет `this` внешнего: для доступа к нестатическим полям нужен объект. Private вложенный класс вне внешнего назвать нельзя.
```cpp
class E {
  struct N {};                  // private
public:
  static N f() { return N{}; }
};
auto n = E::f();  // ок: имя N не названо; E::N x; — ошибка
```
Подвох: объект закрытого типа использовать можно (через `auto`), называть тип — нельзя.
См.: language/nested_classes

## cpp-c-0313 · cpp-t-037
Что такое делегирующий конструктор?
---
Конструктор, в списке инициализации которого стоит имя самого класса — вызов другого конструктора того же класса. Сначала выполняется целевой конструктор, затем тело делегирующего.
```cpp
struct C {
  int x, y;
  C(int x, int y) : x(x), y(y) {}
  C(int x) : C(x, 0) {}
};
```
Подвох: в таком списке нельзя инициализировать другие члены и базы; циклическое делегирование — ошибка. [не по cppreference]
См.: language/initializer_list

## cpp-c-0314 · cpp-t-037
Как создать объект в заранее выделенной памяти с явным вызовом конструктора?
---
Placement new: `new (ptr) T(args)` передаёт `ptr` как дополнительный аргумент функции размещения, которая возвращает его без выделения памяти, и конструирует объект там. Нужен для пулов, арен, контейнеров с зарезервированной памятью.
```cpp
alignas(T) unsigned char buf[sizeof(T)];
T* p = new (buf) T;
p->~T(); // вручную
```
Подвох: деструктор нужно вызвать явно, `delete` неприменим; память должна быть достаточной и выровненной; нужен `<new>`.
См.: language/new, language/destructor

## cpp-c-0335 · cpp-t-037
В чём состоит идиома copy-and-swap?
---
Оператор присваивания копирует источник во временный объект и обменивает с ним ресурс (`swap`); старое состояние уничтожается вместе с временным. Так присваивание использует конструктор копирования и деструктор.
```cpp
T& operator=(const T& other) {
  T temp(other);
  swap(temp);   // swap — noexcept-член
  return *this;
}
```
Подвох: гарантия исключений строгая (при броске в копировании `*this` не тронут), самоприсваивание безопасно; вариант с параметром по значению (`T other`) делает то же. Идея из примера rule of three.
См.: language/rule_of_three

## cpp-c-0342 · cpp-t-037
Что такое `std::initializer_list` и как написать конструктор от него?
---
Лёгкий прокси к массиву `const T` (заголовок `<initializer_list>`): создаётся из `{...}`, когда конструктор принимает такой параметр; копирование не копирует элементы. Есть `size()`, `begin()`, `end()`.
```cpp
struct V {
  std::vector<int> v;
  V(std::initializer_list<int> l) : v(l) {}
};
V a = {1, 2, 3};
```
Подвох: элементы только для чтения; шаблонный параметр `T` по `{1,2,3}` не выводится; `auto x = {1,2,3}` — это `initializer_list<int>`.
См.: utility/initializer_list

## cpp-c-0315 · cpp-t-038
Как обычно реализуют бинарный арифметический оператор для пользовательского типа?
---
Составной `operator+=` — член класса (меняет `*this`, возвращает `T&`), а `operator+` — свободная функция, выраженная через `+=`: так оба операнда участвуют в неявных преобразованиях. Связанные операторы должны делать согласованное действие.
```cpp
T operator+(T a, const T& b) {
  a += b;
  return a;
}
```
Подвох: левый операнд берётся по значению — это нужная копия; `operator+` как член не позволит неявно преобразовать левый аргумент (`2 + a` не скомпилируется).
См.: language/operators

## cpp-c-0316 · cpp-t-038
Как различают перегрузки префиксного и постфиксного `++`?
---
Префиксный: `T& operator++()` — меняет объект, возвращает его же. Постфиксный: `T operator++(int)` — фиктивный `int` лишь отличает перегрузку (при вызове передаётся 0) и возвращает копию старого значения.
```cpp
T& operator++() { ++v; return *this; }
T operator++(int) { T old = *this; ++*this; return old; }
```
Подвох: тип возврата стандарт не фиксирует, но принято как у встроенных; постфиксная форма дороже из-за копии.
См.: language/operator_incdec

## cpp-c-0336 · cpp-t-038
Как работает оператор `<=>` и как определить его для своего типа?
---
Three-way comparison (C++20) возвращает `std::strong_ordering`, `weak_ordering` или `partial_ordering`. Дефолтный `<=>` сравнивает базы, затем нестатические поля в порядке объявления; для него неявно объявляется и `==`, а `<`, `>`, `<=`, `>=` переписываются через `<=>`.
```cpp
struct V {
  int a, b;
  auto operator<=>(const V&) const = default;
};
```
Подвох: неявный `==` появляется только при defaulted `<=>`; если `<=>` написан вручную, `operator==` нужно объявить отдельно. Не перегружаются `::`, `.`, `.*`, `?:`; приоритет и ассоциативность изменить нельзя.
См.: language/default_comparisons, language/operators

## cpp-c-0317 · cpp-t-039
Что запрещает `const` у нестатического метода?
---
`const` после списка параметров делает объект внутри метода константным: метод не может изменять нестатические поля и вызывать неконстантные методы. Исключение — поля `mutable`.
```cpp
struct A {
  int n; mutable int cache;
  void f() const { cache = 1; n = 2; } // n: ошибка
};
```
Подвох: `mutable` нельзя для статических полей, ссылок и `int* const`; применяют к кэшам, мьютексам, счётчикам, не влияющим на видимое состояние.
См.: language/cv

## cpp-c-0318 · cpp-t-039
Что происходит с объектом, на который указывает поле-указатель, внутри `const`-метода?
---
Сам указатель становится `T* const` (его нельзя перенаправить), но указуемый объект не становится константным — его можно изменять. Для ссылочного поля то же: ссылку не переприсвоить, объект изменяем.
```cpp
struct A {
  int* p;
  void f() const { *p = 1; } // ок; p = nullptr — ошибка
};
```
Подвох: константность не «глубокая»: чтобы запретить запись, нужен `const int*`.
См.: language/cv, language/data_members

## cpp-c-0339 · cpp-t-039
Как определяют и инициализируют статические поля класса, в частности константные?
---
Статическое поле — одна переменная на программу, не связанная с объектами. Объявление в классе (`static`) не является определением: определение вне класса без `static`. Исключения: `const static` целочисленного/enum-типа с константным инициализатором в классе; `constexpr static` обязан иметь инициализатор в классе; `inline static` (C++17) определяется в классе.
```cpp
struct X { static int n; static constexpr int k = 5; };
int X::n = 1; // определение
```
Подвох: `const static int` без определения вне класса можно использовать по значению, но нельзя брать адрес (не ODR-usable); статические переменные сначала получают constant- или zero-инициализацию, затем (при необходимости) динамическую.
См.: language/static, language/initialization

## cpp-c-0319 · cpp-t-040
Как объявить оператор преобразования класса в `int`?
---
Функцией-членом `operator int() const` — без типа возврата, имя задаёт целевой тип. С `explicit` (C++11) она участвует только в прямой инициализации и явных приведениях.
```cpp
struct B {
  int v;
  explicit operator int() const { return v; }
};
B b{1}; int n = static_cast<int>(b);
```
Подвох: без `explicit` преобразование неявное (`int m = b;`) и может срабатывать неожиданно; цель преобразования не может быть массивом или функцией.
См.: language/cast_operator, language/explicit

## cpp-c-0320 · cpp-t-040
Чем contextual conversion в `bool` отличается от обычного неявного преобразования?
---
Contextual conversion к `bool` (условие `if`/`while`/`for`, операнды `!`, `&&`, `||`, первый операнд `?:`, `static_assert`, `noexcept`) допустима, если корректно `bool t(e);`, поэтому учитывает и `explicit operator bool()`. Обычное неявное преобразование — copy-initialization `bool t = e;`, explicit-функции в нём не участвуют.
```cpp
struct S { explicit operator bool() const; };
S s; if (s) {}     // ок
bool b = s;        // ошибка
```
Подвох: `return s;` из функции, возвращающей `bool`, тоже ошибка — это copy-initialization.
См.: language/implicit_conversion, language/explicit

## cpp-c-0343 · cpp-t-040
Как определить пользовательский литеральный суффикс (например, `_bi` для `BigInteger`)?
---
Определить литеральный оператор `operator""_bi`; встретив `123_bi`, компилятор ищет `operator""_bi`. Для целого литерала: если есть перегрузка с `unsigned long long`, берётся она; иначе raw-оператор `const char*` получает литерал строкой, что нужно для чисел больше `ULL`.
```cpp
BigInteger operator""_bi(const char* digits) {
  return BigInteger(digits);
}
auto x = 123456789012345678901234567890_bi;
```
Подвох: если токен подходит и под обычный литерал, он обычный (нельзя перегрузить `LL`); нет подходящего оператора — ошибка.
См.: language/user_literal

## cpp-c-0321 · cpp-t-041
Что происходит, если метод наследника имеет то же имя, что методы родителя?
---
Неквалифицированный поиск находит имя в области наследника и останавливается: все одноимённые перегрузки родителя скрыты, даже с другой сигнатурой. Вернуть их можно using-declaration `using Base::f;` — вводит все перегрузки.
```cpp
struct B { void f(int); };
struct D : B { void f(); using B::f; };
// без using: D().f(1) — ошибка
```
Подвох: сначала поиск имён, потом разрешение перегрузки, и только в конце проверка доступа — скрытие не зависит от private/public.
См.: language/derived_class, language/using_declaration, language/unqualified_lookup

## cpp-c-0322 · cpp-t-041
Как явно вызвать скрытый метод родителя у объекта-наследника?
---
Квалифицированным именем с классом родителя: `d.Base::f(1)` (или `Base::f(1)` в методе наследника). Имя справа от `::` ищется в области этого класса.
```cpp
D d;
d.B::f(1); // вызов B::f, не скрытой D::f
```
Подвох: квалифицированное имя подавляет виртуальный вызов: `br.Base::f()` вызовет версию `Base`, даже если есть override.
См.: language/qualified_lookup, language/virtual

## cpp-c-0344 · cpp-t-041
Как унаследовать конструкторы базового класса?
---
using-declaration `using Base::Base;` в производном классе делает все конструкторы базы доступными разрешению перегрузки. Выбранный унаследованный конструктор инициализирует подобъект базы, остальные базы и поля — как у конструктора по умолчанию.
```cpp
struct B { B(int, int); };
struct D : B { using B::B; int x = 0; };
D d(1, 2);
```
Подвох: сам `using` не создаёт конструктор по умолчанию для `D`; доступность определяется как у конструктора базы.
См.: language/using_declaration

## cpp-c-0345 · cpp-t-041
Как явно инициализировать базу в конструкторе наследника?
---
В списке инициализации производного конструктора указывается имя базы с аргументами: `D(int x) : B(x) {}`. Конструкторы баз вызываются до инициализации полей наследника; без явного вызова нужен конструктор по умолчанию базы.
```cpp
struct B { int n; B(int x) : n(x) {} };
struct D : B { D() : B(5) {} };
```
Подвох: виртуальную базу инициализирует только самый производный класс, и такие подобъекты строятся раньше невиртуальных.
См.: language/derived_class

## cpp-c-0323 · cpp-t-042
Чем публичное наследование отличается от приватного с точки зрения преобразования к базовому классу?
---
При публичном наследовании `Derived*`/`Derived&` неявно преобразуются к базе в любом коде. При приватном «derived IS-A base» только внутри членов самого производного класса (и друзей), не в коде снаружи и не в далее-производных.
```cpp
struct B {};
struct D : private B {};
D d; B* p = &d; // ошибка: B недоступна
```
Подвох: `static_cast` к недоступной базе тоже ошибка, а C-style cast при недоступной базе игнорирует `private`; проверка доступа делается после остальных шагов.
См.: language/derived_class, language/access, language/explicit_cast

## cpp-c-0324 · cpp-t-042
Как различаются значения доступа по умолчанию у `class` и `struct`?
---
У `class` члены и база по умолчанию `private`, у `struct` — `public`; у `union` члены `public`. Других отличий нет.
```cpp
struct S : B {};  // как : public B
class  C : B {};  // как : private B
```
Подвох: при приватном наследовании public и protected члены базы становятся private в производном; private члены базы недоступны всегда; дружба не наследуется.
См.: language/access, language/derived_class, language/friend

## cpp-c-0325 · cpp-t-043
Почему обращение к члену при множественном наследовании может быть неоднозначным?
---
Если имя найдено в нескольких базовых подобъектах, поиск неоднозначен — ошибка компиляции, пока имя не квалифицировано. Проверка идёт до доступности.
```cpp
struct A { int x; }; struct B { int x; };
struct C : A, B {};
C c;
c.x = 1;    // ошибка
c.A::x = 1; // ок
```
Подвох: ошибка и при разных типах, и если один из членов недоступен (поиск — до проверки доступа).
См.: language/derived_class, language/access, language/qualified_lookup

## cpp-c-0326 · cpp-t-043
Почему адрес указателя на базовый подобъект может отличаться от адреса полного объекта?
---
Каждая база лежит в объекте на ABI-зависимом смещении; при нескольких базах не все лежат в начале. Неявное преобразование `C*` в `B*` и `static_cast` учитывают смещение, а `reinterpret_cast` копирует то же значение.
```cpp
C c;
B* p = &c;                        // сдвиг учтён
B* q = reinterpret_cast<B*>(&c);  // ошибка: указывает не на B
```
Подвох: смещение зависит от реализации; `static_cast` вниз (`B*` в `C*`) обратно вычтет смещение, а к виртуальной базе — вообще не допускается.
См.: language/derived_class, language/reinterpret_cast, language/static_cast

## cpp-c-0346 · cpp-t-043
В чём проблема ромбовидного наследования и как её решает виртуальное наследование?
---
При `D : B, C`, где `B` и `C` наследуют `A`, объект `D` содержит два подобъекта `A`; `d.n` неоднозначно. При `virtual`-наследовании от `A` в самом производном объекте один общий подобъект `A`; его конструктор вызывает только самый производный класс.
```cpp
struct A { int n; };
struct B : virtual A {};
struct C : virtual A {};
struct D : B, C {};  // d.n однозначно
```
Подвох: `static_cast` от виртуальной базы к производному — ошибка; без `virtual` к `A` нужно обращаться как `d.B::n`.
См.: language/derived_class, language/static_cast

## cpp-c-0327 · cpp-t-044
Для чего нужен `dynamic_cast`?
---
Безопасное приведение по иерархии вверх, вниз и вбок. Для нисходящего и бокового случаев выражение должно быть указателем/ссылкой на полиморфный тип; в runtime проверяется, что объект содержит целевой класс (публичная однозначная база). Неудача: `nullptr` для указателя, `std::bad_cast` для ссылки.
```cpp
Base* b = new Derived;
if (auto* d = dynamic_cast<Derived*>(b)) { /* ок */ }
```
Подвох: `dynamic_cast<void*>` даёт указатель на самый производный объект; `static_cast` вниз быстрее, но безопасен только если тип гарантирован.
См.: language/dynamic_cast, types/bad_cast

## cpp-c-0328 · cpp-t-044
Какой тип должен быть полиморфным для проверяемого нисходящего `dynamic_cast`?
---
Тип выражения-операнда (указатель или ссылка) должен быть полиморфным: класс объявляет или наследует хотя бы одну виртуальную функцию. Иначе runtime-проверка невозможна, и приведение не компилируется.
```cpp
struct A { int a; };
struct B : A {};
A* p = new B;
auto* q = dynamic_cast<B*>(p); // ошибка: A не полиморфный
```
Подвох: приведение вверх (к базе) работает без полиморфности — это разрешено на этапе компиляции.
См.: language/dynamic_cast

## cpp-c-0337 · cpp-t-044
Что делает `typeid` и как сравнивать типы?
---
`typeid(тип или выражение)` возвращает ссылку на `const std::type_info`. Для glvalue полиморфного типа берётся динамический тип (выражение вычисляется), иначе — статический, без вычисления. Типы сравнивают `==`/`!=`, имя даёт `name()` (формат зависит от реализации).
```cpp
struct B { virtual ~B() = default; }; struct D : B {};
D d; B& r = d;
bool same = typeid(r) == typeid(D); // true
```
Подвох: `typeid(const T) == typeid(T)`; `*p` с нулевым `p` у полиморфного типа бросает `std::bad_typeid`; адреса `type_info` могут различаться, сравнивать надо `==`.
См.: language/typeid, types/type_info

## cpp-c-0329 · cpp-t-045
Что обычно содержит vtable?
---
Типичная реализация (Itanium ABI: GCC, Clang): у каждого полиморфного класса таблица с адресами виртуальных функций (в порядке объявления) и служебными полями (смещение до полного объекта, указатель на `type_info` для RTTI). Объект хранит скрытый указатель `vptr` на неё.
Подвох: стандарт vtable не упоминает; виртуальный вызов — косвенный вызов через `vptr`, а квалифицированный (`Base::f()`) вызывается напрямую. [не по cppreference]
См.: language/virtual

## cpp-c-0330 · cpp-t-045
Почему пустой класс с виртуальной функцией обычно занимает больше места, чем пустой класс без неё?
---
Пустой класс имеет `sizeof` ≥ 1, чтобы разные объекты имели разные адреса. Класс с виртуальной функцией содержит скрытый `vptr` на vtable — обычно 8 байт на 64-битной платформе.
```cpp
struct E {};                      // sizeof == 1
struct P { virtual void f() {} }; // обычно 8 (x86-64)
```
Подвох: точные размеры не заданы стандартом; пустая база обычно не увеличивает размер производного (EBO), с `vptr` — увеличивает. [не по cppreference]
См.: language/virtual

## cpp-c-0338 · cpp-t-045
Что меняется, если родитель верхнего уровня не полиморфный, а наследник полиморфный?
---
Полиморфен только наследник: типично `vptr` лежит в начале объекта, а подобъект неполиморфной базы идёт после него. Поэтому `Derived*` → `Base*` сдвигает адрес, а `dynamic_cast` из `Base*` невозможен (база не полиморфна).
```cpp
struct A { int a; };
struct B : A { virtual void f() {} };
// типично: vptr, затем A::a; sizeof(B) == 16
```
Подвох: виртуальный вызов через `A*` невозможен — у `A` нет `vptr`. [не по cppreference]
См.: language/virtual, language/dynamic_cast

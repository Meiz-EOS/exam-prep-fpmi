## cpp-c-0401 · cpp-t-046
Как выбирается перегрузка между обычной функцией и шаблонной функцией?
---
Побеждает кандидат с лучшими неявными преобразованиями аргументов; если они одинаково хороши, не-шаблон предпочтительнее специализации шаблона, а между двумя шаблонами берётся более специализированный.
```cpp
void f(int) {}
template<class T> void f(T) {}
f(1);   // обычная f(int)
f('a'); // шаблон, T = char: точное совпадение лучше повышения char -> int
```
Подвох: при выводе `T` неявные преобразования не применяются, поэтому шаблон часто даёт точное совпадение там, где обычной функции нужно приведение.
См.: language/overload_resolution, language/template_argument_deduction

## cpp-c-0402 · cpp-t-047
Чем специализация шаблона функции отличается от перегрузки?
---
Специализация не участвует в выборе перегрузки: сначала выбирается первичный шаблон (или перегрузка), и только потом, если выбран шаблон, берётся его подходящая специализация. Перегрузка — отдельный кандидат.
```cpp
template<class T> void f(T) {}      // 1
template<class T> void f(T*) {}     // 2 — перегрузка
template<> void f<int*>(int*) {}    // специализация шаблона 1
int x; f(&x);                       // вызовется 2, специализация игнорируется
```
Подвох: частично специализировать шаблон функции нельзя (только полностью); у специализации нельзя задавать аргументы по умолчанию.
См.: language/template_specialization, language/function_template

## cpp-c-0433 · cpp-t-047
Приведите пример неоднозначности при выборе частичной специализации класса.
---
Если подходят несколько частичных специализаций и ни одна не более специализированная, программа не компилируется; если подходит одна — используется она, если ни одна — первичный шаблон.
```cpp
template<class T, class U> struct S {};         // первичный
template<class T> struct S<T, int> {};          // #1
template<class U> struct S<int, U> {};          // #2
S<int, int> s;                                  // ошибка: #1 и #2 неоднозначны
```
Подвох: лечится дополнительной специализацией `S<int, int>`, более специализированной, чем обе; частичные специализации возможны только для классов и (C++14) переменных, не для функций.
См.: language/partial_specialization

## cpp-c-0434 · cpp-t-047
Что такое инстанцирование шаблона и двухэтапная компиляция?
---
Шаблон сам по себе не тип и не функция: код порождается при инстанцировании, когда специализация нужна в контексте, требующем полного типа или определения функции. Независимые имена ищутся и связываются в точке определения шаблона, поиск зависимых имён откладывается до подстановки аргументов (ADL учитывает и контекст инстанцирования).
```cpp
void g(double) {}
template<class T> void f() { g(1); } // g — независимое имя, связано сейчас
void g(int) {}
// f<int>() вызовет g(double)
```
Подвох: определение шаблона класса должно быть видно в точке неявного инстанцирования (шаблоны живут в заголовках); явная специализация должна быть объявлена до первого неявного инстанцирования; член шаблона класса инстанцируется только при использовании.
См.: language/dependent_name, language/templates, language/template_specialization

## cpp-c-0403 · cpp-t-048
Как задать простое вычисление Фибоначчи на этапе компиляции?
```cpp
#include <cstddef>
constexpr unsigned long long fib(std::size_t n) {
    return n < 2 ? n : fib(n - 1) + fib(n - 2);
}
static_assert(fib(10) == 55);
```
---
`constexpr` разрешает вычисление при компиляции, а `static_assert` требует, чтобы `fib(10)` было константным выражением со значением 55. Шаблонный вариант: `template<int N> struct Fib { static constexpr int value = Fib<N-1>::value + Fib<N-2>::value; };` и полные специализации `Fib<0>`, `Fib<1>`.
Подвох: `constexpr`-функция вычисляется при компиляции только в константном контексте; вне него может исполняться в рантайме. Экземпляры `Fib<N>` создаются один раз, а наивная рекурсия `fib` экспоненциальна.
См.: language/constexpr, language/template_metaprogramming

## cpp-c-0416 · cpp-t-048
Что будет при слишком глубокой шаблонной рекурсии и как это настроить?
---
Стандарт рекомендует поддерживать не менее 1024 уровней рекурсивного инстанцирования, а бесконечная рекурсия при инстанцировании — неопределённое поведение. На практике компилятор останавливается с ошибкой по лимиту глубины; в GCC и Clang его поднимают флагом `-ftemplate-depth=N`.
Подвох: `Fib<N>` без специализаций-баз `Fib<0>`, `Fib<1>` рекурсирует бесконечно; рост лимита увеличивает расход памяти и времени компиляции. Флаг и значения по умолчанию (около 900 у GCC, 1024 у Clang) [не по cppreference].
См.: language/template_metaprogramming

## cpp-c-0404 · cpp-t-049
Что проверяет `std::is_same`?
---
`std::is_same<T, U>::value` истинно, только если `T` и `U` называют один и тот же тип (с учётом `const`/`volatile`); `std::is_same_v<T, U>` (C++17) даёт то же значение. Реализация: основной шаблон наследует `false_type`, частичная специализация `<T, T>` — `true_type`.
```cpp
static_assert(std::is_same_v<int, signed int>);
static_assert(!std::is_same_v<int, const int>);
static_assert(!std::is_same_v<char, signed char>);
```
Подвох: проверка идёт на этапе компиляции, а `typeid(T) == typeid(U)` — в рантайме и игнорирует верхние cv-квалификаторы и ссылки; добавлять специализации `is_same` — UB.
См.: types/is_same

## cpp-c-0417 · cpp-t-049
Зачем нужно `typename` при обращении к зависимому имени и чем `std::remove_const` отличается от `const_cast`?
---
Имя вида `T::x`, зависящее от параметра шаблона, по умолчанию считается не типом; `typename T::type` сообщает, что это тип. `std::remove_const<T>::type` (алиас `remove_const_t`, C++14) работает на уровне типов и снимает только верхний `const`, а `const_cast` меняет выражение в рантайме.
```cpp
template<class T>
void f() {
    typename T::value_type v{};                // без typename — не объявление
    using U = std::remove_const_t<const int>;  // int
}
```
Подвох: `remove_const<const int*>` оставляет тип без изменений (указатель сам не `const`); `T::x * y;` без `typename` читается как умножение; `const_cast` на реально константном объекте с записью — UB.
См.: language/dependent_name, types/remove_cv

## cpp-c-0405 · cpp-t-050
Что такое пакет параметров в variadic template?
---
Пакет параметров шаблона (`class... Ts`) принимает ноль или больше аргументов; пакет параметров функции `Ts... args` принимает ноль или больше аргументов вызова. Распаковка `pattern...` разворачивает шаблон в список по элементам пакета, `sizeof...(Ts)` — число элементов (`std::size_t`).
```cpp
void print() {}
template<class T, class... Ts>
void print(const T& h, const Ts&... t) { std::cout << h; print(t...); } // откусываем первый
```
Подвох: пакет может быть пустым, поэтому нужна база рекурсии; в первичном шаблоне класса пакет должен стоять последним в списке параметров.
См.: language/parameter_pack, language/sizeof...

## cpp-c-0406 · cpp-t-051
Что происходит при `throw` объекта и как повторно выбросить перехваченное исключение без копирования?
---
`throw expr` создаёт объект исключения с динамической длительностью хранения: он копи-инициализируется из `expr` (тип — статический, без верхних cv), память выделяется неуказанным способом, но не глобальными функциями выделения; затем стек раскручивается. `throw;` реактивирует текущий объект, новый не создаётся.
```cpp
try { throw Derived{}; }
catch (Base& e) {
    throw;      // тот же объект, динамический тип Derived
    // throw e; // новая копия Base — срезка
}
```
Подвох: `catch (Base e)` по значению копирует объект ещё раз (и срезает); ловить нужно по ссылке.
См.: language/throw, language/catch

## cpp-c-0418 · cpp-t-051
Чем выбор блока `catch` отличается от перегрузки функций?
---
Обработчики проверяются строго по порядку записи, выбирается первый подходящий — лучшего совпадения не ищут. Подходит тот же тип (без верхнего cv) или однозначный публичный базовый класс (для указателей — стандартное преобразование указателя); `catch (...)` ловит всё и стоит только последним.
```cpp
try { throw Derived{}; }
catch (Base&)    { /* сработает этот, хотя ниже точнее */ }
catch (Derived&) { /* недостижим */ }
```
Подвох: если подходящего обработчика нет, вызывается `std::terminate`, раскрутка стека при этом implementation-defined; производные ловят раньше базовых.
См.: language/catch

## cpp-c-0407 · cpp-t-052
Что происходит с уже созданными подобъектами, если конструктор объекта выбрасывает исключение?
---
Для всех полностью сконструированных нестатических членов и баз вызываются деструкторы в обратном порядке завершения конструкторов; деструктор самого объекта не вызывается (кроме случая делегирующего конструктора после завершения целевого, C++11).
```cpp
S::S() try : a_(1), b_(2) { /* тело */ }
catch (...) { /* a_, b_ уже уничтожены; в конце обработчика исключение выбрасывается снова */ }
```
Подвох: ресурсы, захваченные в теле вручную, утекут — нужен RAII; function-try-block ловит и исключения списка инициализации, но перевыбрасывает их автоматически [не по cppreference].
См.: language/throw, language/initializer_list

## cpp-c-0419 · cpp-t-052
Почему исключения из деструктора опасны и чем `std::uncaught_exceptions` лучше `std::uncaught_exception`?
---
Деструкторы по умолчанию `noexcept` (C++11); исключение, вышедшее из `noexcept`-функции, вызывает `std::terminate`. `uncaught_exception()` возвращает `bool` — идёт ли раскрутка, а `uncaught_exceptions()` (C++17) — число ещё не пойманных исключений в потоке.
```cpp
struct Guard {
    int n = std::uncaught_exceptions();
    ~Guard() { bool unwinding = std::uncaught_exceptions() > n; (void)unwinding; }
};
```
Подвох: `uncaught_exception()` устарела в C++17 и удалена в C++20; при `true` бывает безопасно бросать, если исключение поймано внутри деструктора, но `bool` не отличает «раскрутка вокруг нас» от «раскрутка началась в нашем теле» — это видно, только сравнив счётчик в конструкторе и деструкторе.
См.: error/uncaught_exception, language/destructor

## cpp-c-0408 · cpp-t-053
Что гарантирует `noexcept` у функции?
---
Обещание, что исключение не покинет функцию: если поиск обработчика доходит до внешнего блока такой функции, вызывается `std::terminate`. Условный `noexcept(expr)` задаётся константным `bool`-выражением; оператор `noexcept(expr)` не вычисляет `expr` и возвращает `true`, если оно объявлено нетрогающим.
```cpp
template<class T>
void f(T& a) noexcept(noexcept(a.g())) { a.g(); }
```
Подвох: с C++17 `noexcept` входит в тип функции; переопределение невыбрасывающей виртуальной функции обязано быть тоже невыбрасывающим; `noexcept(expr) == true` не исключает исключения из-за UB; `throw()` удалён в C++20.
См.: language/noexcept_spec, language/noexcept

## cpp-c-0420 · cpp-t-053
Что такое базовая и строгая гарантии безопасности относительно исключений?
---
Базовая: при исключении программа в корректном состоянии, нет утечек, инварианты целы, но значения могут измениться. Строгая: состояние откатывается к тому, что было до вызова (пример — `std::vector::push_back`). Остальные уровни: nothrow и отсутствие гарантий.
Подвох: nothrow ожидается от деструкторов, `swap` и перемещающих конструкторов — на них строится строгая гарантия; «exception-neutral» значит, что исключение из параметра шаблона (например, из `Compare`) пробрасывается без изменений.
См.: language/exceptions

## cpp-c-0409 · cpp-t-054
Как избежать дублирования реализации константного и неконстантного итераторов в контейнере?
---
Сделать один шаблон итератора с параметром `bool IsConst` и выбирать типы через `std::conditional_t`: для `iterator` — `T*`/`T&`, для `const_iterator` — `const T*`/`const T&`.
```cpp
template<bool IsConst>
struct Iter { // внутри Vector<T>
    using pointer = std::conditional_t<IsConst, const T*, T*>;
    pointer ptr;
};
using iterator = Iter<false>; using const_iterator = Iter<true>;
```
Подвох: нужна неявная конвертация `iterator` в `const_iterator`, обратной быть не должно. [не по cppreference]
См.: iterator/iterator_traits

## cpp-c-0421 · cpp-t-054
Для чего нужен `std::iterator_traits` и чем `std::advance` отличается от `std::distance` для разных итераторов?
---
`iterator_traits<It>` даёт типы итератора (`iterator_category`, `value_type`, `difference_type`, `pointer`, `reference`), в том числе для сырых указателей. `advance` и `distance` выбирают алгоритм по категории: у random access — O(1), у остальных — линейный шаг `++`.
Подвох: диспетчеризация делается по тегу `iterator_category` (перегрузкой или `if constexpr`); для input/forward итераторов `advance` с отрицательным `n` — UB, `distance(first, last)` требует достижимости `last` из `first`.
См.: iterator/iterator_traits, iterator/advance, iterator/distance

## cpp-c-0422 · cpp-t-054
Как устроен `std::reverse_iterator` и что возвращает его `base()`?
---
`reverse_iterator` — адаптер над двунаправленным итератором: `++` вызывает `--` базового, `base()` возвращает хранимый базовый итератор. Для `r`, построенного от `i`, всегда `&*r == &*(i - 1)`, поэтому `reverse_iterator` от `end()` разыменовывается в последний элемент.
```cpp
std::vector<int> v{1, 2, 3};
std::reverse_iterator<std::vector<int>::iterator> r(v.end());
// *r == 3, r.base() == v.end()
```
Подвох: `rbegin()` строится от `end()`, `rend()` от `begin()`; реализация разыменовывает `*std::prev(current)`; не работает с «stashing»-итераторами, чей `*` возвращает ссылку на член самого итератора.
См.: iterator/reverse_iterator

## cpp-c-0410 · cpp-t-055
Какие три указателя обычно описывают динамический буфер `vector`?
---
Начало буфера, конец построенных элементов и конец выделенной ёмкости: `begin`, `end`, `capacity_end`; `size() == end - begin`, `capacity() == capacity_end - begin`. Встречается и схема «указатель + `size` + `capacity`».
Подвох: стандарт не фиксирует поля, это устройство libstdc++ и libc++. Элементы между `end` и `capacity_end` — сырая память, объекты в ней не созданы. [не по cppreference]
См.: container/vector

## cpp-c-0423 · cpp-t-055
Как реализуются `reserve` и `push_back` и какие итераторы они инвалидируют?
---
`reserve(n)` при `n > capacity()` выделяет новый буфер, переносит или копирует элементы, уничтожает старые и освобождает прежнюю память. `push_back` при `size == capacity` сначала увеличивает ёмкость (обычно вдвое), затем строит элемент в конце. Реализация [не по cppreference].
Подвох: по cppreference, `reserve` и `push_back` инвалидируют все итераторы, указатели и ссылки, если ёмкость изменилась; иначе `reserve` не инвалидирует ничего, а `push_back` — только `end()`.
См.: container/vector

## cpp-c-0424 · cpp-t-055
Чем `std::vector<bool>` отличается от обычного `vector`?
---
Это специализация, которая может быть экономной по памяти (реализация определяет как; типично — по биту на элемент); `operator[]` возвращает по значению прокси-объект `std::vector<bool>::reference`, а не `bool&`.
```cpp
std::vector<bool> v(8);
auto r = v[0]; // прокси, не bool
r = true;      // изменяет бит внутри v
```
Подвох: элементы не обязательно лежат непрерывно, `&v[0]` не даёт `bool*`; разные элементы нельзя безопасно менять из разных потоков; `std::allocator_traits::construct` для битов не используется.
См.: container/vector_bool

## cpp-c-0411 · cpp-t-056
Как в общих чертах устроен `std::deque`?
---
Элементы хранятся не непрерывно: типичная реализация — последовательность отдельно выделенных массивов фиксированного размера плюс служебная структура (карта указателей на блоки). Поэтому индексный доступ O(1), но с двумя разыменованиями указателя, а добавление в оба конца не копирует старые элементы.
Подвох: даже один элемент занимает целый внутренний блок (у libstdc++ блок 512 байт (или 1 элемент, если он больше), у libc++ — 16 элементов или 4096 байт); вставка и удаление с концов не инвалидируют указатели и ссылки на остальные элементы. Устройство «карта + блоки» стандартом не задано [не по cppreference].
См.: container/deque

## cpp-c-0425 · cpp-t-056
Какие итераторы, указатели и ссылки инвалидирует вставка в `std::deque`?
---
Вставка в начало или конец (`push_front`, `push_back`, `emplace_*`) инвалидирует все итераторы, но не указатели и ссылки на элементы. Вставка в середину инвалидирует всё: итераторы, указатели и ссылки.
Подвох: `erase` в начале или конце инвалидирует только стёртые элементы (при стирании в конце — ещё `end()`); `erase` в середине инвалидирует всё.
См.: container/deque

## cpp-c-0426 · cpp-t-056
Какие методы есть у `deque`, но нет у `vector`, и наоборот?
---
Только у `deque`: `push_front`, `emplace_front`, `pop_front`. Только у `vector`: `capacity`, `reserve`, `data`.
Подвох: у `deque` есть `shrink_to_fit`, но нет `capacity` и `reserve`; нет `data()`, потому что память не непрерывна, поэтому указатель на элемент не годится для арифметики за его пределы.
См.: container/deque, container/vector

## cpp-c-0412 · cpp-t-057
Какие итераторы, указатели и ссылки инвалидирует вставка элемента в `std::list`?
---
Вставка, удаление и перемещение элементов не инвалидируют итераторы и ссылки на другие элементы. Недействителен только итератор (и указатель или ссылка) на удалённый элемент.
Подвох: `splice` между списками тоже сохраняет итераторы, они указывают на те же элементы, но уже в другом списке; `end()` остаётся действительным.
См.: container/list

## cpp-c-0427 · cpp-t-057
Как устроен `std::list` внутри и как реализованы `begin()`/`end()`?
---
Обычно это кольцевой двусвязный список с фиктивным узлом `BaseNode` (только `prev`/`next`), а `Node` наследует его и хранит значение. `end()` — итератор на фиктивный узел, `begin()` — на `fake.next`.
Подвох: фиктивный узел делает пустой список однородным (нет проверок на `nullptr`), а `--end()` даёт последний элемент; сам `end()` разыменовывать нельзя. [не по cppreference]
См.: container/list

## cpp-c-0428 · cpp-t-057
Какие асимптотики и идеи у специфичных методов `std::list`: `splice`, `sort`, `merge`, `reverse`?
---
`splice` перешивает указатели узлов без копирования элементов (O(1) для целого списка или одного элемента); `sort` — O(N log N), слияние; `merge` объединяет два отсортированных списка за линейное время; `reverse` — O(N).
Подвох: `std::sort` для `list` не подходит (нужен random access); `std::forward_list` — односвязный: итерация только вперёд, зато компактнее, методы `*_after`.
См.: container/list, container/forward_list

## cpp-c-0413 · cpp-t-058
Что хранит `std::pair` и что делает `std::make_pair`?
---
`std::pair<T1, T2>` хранит два значения в полях `first` и `second`; `std::make_pair(a, b)` создаёт пару с выведенными типами.
```cpp
auto p = std::make_pair(1, 2.5); // pair<int, double>
std::pair q{1, 2.5};             // C++17 CTAD
```
Подвох: `make_pair` применяет `decay` (массивы и функции -> указатели), `std::reference_wrapper<T>` превращается в `T&`; `value_type` у `map` — `pair<const Key, T>`.
См.: utility/pair

## cpp-c-0429 · cpp-t-058
Как устроен `std::map` внутри и как работает итератор?
---
Обычно `map` — красно-чёрное дерево узлов с `pair<const Key, T>`; поиск, вставка и удаление за O(log N); итераторы идут по возрастанию ключа. Итератор хранит указатель на узел; инкремент амортизированно O(1), обход всего `map` — O(N), `end()` — фиктивная вершина (часть про итератор и фиктивную вершину [не по cppreference]).
Подвох: `insert` не инвалидирует итераторы и ссылки, `erase` — только относящиеся к удалённым элементам.
См.: container/map

## cpp-c-0430 · cpp-t-058
Чем `operator[]` у `std::map` отличается от `at()`?
---
`m[key]` при отсутствии ключа вставляет элемент со значением по умолчанию и возвращает ссылку на него. `at(key)` не вставляет, а при отсутствии ключа бросает `std::out_of_range`.
```cpp
std::map<int, int> m;
m[5];     // вставлено {5, 0}
m.at(7);  // out_of_range
```
Подвох: `operator[]` нельзя вызывать для `const map` и значения без конструктора по умолчанию; `find` и `insert` возвращают итератор / `pair<iterator, bool>`.
См.: container/map

## cpp-c-0414 · cpp-t-059
Для чего предназначен `std::string_view`?
---
Это невладеющее представление непрерывной последовательности символов (C++17): хранит указатель и длину, читает строку без копирования, но не продлевает срок жизни символов.
```cpp
std::string_view sv = "hello world";
sv.remove_prefix(6); // "world", без копирования
```
Подвох: `string_view` не обязан оканчиваться нулём (не передавать `data()` в C-функции); `std::string_view v = std::string("tmp");` оставляет висячую ссылку после `;`.
См.: string/basic_string_view

## cpp-c-0431 · cpp-t-059
Что такое `std::span` и чем он отличается от `std::string_view`?
---
`std::span<T>` (C++20) — невладеющее представление непрерывной последовательности произвольных элементов; `span<const T>` только читает, `span<T>` может изменять. Методы: `size`, `data`, `operator[]`, `first`, `last`, `subspan`.
Подвох: у `span` может быть статическая длина (`span<T, N>`); как и `string_view`, не продлевает время жизни данных и висит после уничтожения источника.
См.: container/span

## cpp-c-0415 · cpp-t-060
Зачем контейнерам нужен аллокатор?
---
Аллокатор отделяет получение и освобождение сырой памяти от создания и уничтожения объектов, позволяя контейнеру настраивать стратегию управления памятью (пулы, арены, отслеживание).
Подвох: `std::allocator<T>::allocate(n)` возвращает неинициализированную память под `n` объектов, объекты не создаются; `deallocate(p, n)` требует того же `n`. `construct`/`destroy` у `std::allocator` убраны в C++20.
См.: memory/allocator, named_req/Allocator

## cpp-c-0432 · cpp-t-060
Зачем нужен `std::allocator_traits` и как с ним правится `vector::reserve`?
---
`allocator_traits<A>` даёт единый интерфейс к аллокатору с значениями по умолчанию для необязательных членов (`construct`, `destroy`, `rebind_alloc`). `reserve` вызывает `traits::allocate`, `traits::construct` и `traits::destroy` вместо `new`/`delete` и placement new, а `traits::deallocate` — для освобождения.
```cpp
using Tr = std::allocator_traits<Alloc>;
T* p = Tr::allocate(alloc, n);
Tr::construct(alloc, p, value);
```
Подвох: аллокатор должен храниться в контейнере как поле; прямой вызов `alloc.construct` не работает с минимальными аллокаторами. Правка `reserve` [не по cppreference].
См.: memory/allocator_traits, memory/allocator

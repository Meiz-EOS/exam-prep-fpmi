## cpp-c-0501 · cpp-t-061
Как формально различают категории значений выражения в C++?
---
Каждое выражение принадлежит ровно одной первичной категории: prvalue, xvalue или lvalue. glvalue — выражение, определяющее идентичность объекта или функции (это lvalue и xvalue); xvalue — glvalue, обозначающий объект, ресурсы которого можно переиспользовать; lvalue — glvalue, не являющийся xvalue; rvalue — prvalue или xvalue. prvalue вычисляет значение операнда или инициализирует объект.
Подвох: `std::move(x)` — xvalue; имя переменной типа `T&&` — lvalue; с C++17 prvalue сам по себе не временный объект, он материализуется только при необходимости.
См.: language/value_category

## cpp-c-0516 · cpp-t-061
Что такое ref-qualifier метода (`&`, `&&`) и как он сочетается с `const`?
---
Ref-qualifier после списка параметров ограничивает вызов по категории объекта: `&` — только на lvalue, `&&` — только на rvalue; без квалификатора метод вызывается на любом. Квалификаторы позволяют перегружать метод по категории `*this`.
```cpp
struct S {
    int& get() &  { return v; }  // для lvalue
    int  get() && { return v; }  // для rvalue
    int v = 0;
};
```
Подвох: `const&` принимает и lvalue, и rvalue (привязка к const-ссылке); `const&&` — только const rvalue. Нельзя смешивать перегрузки с ref-qualifier и без него при одинаковых параметрах.
См.: language/member_functions

## cpp-c-0517 · cpp-t-061
Приведите пример rvalue, которому можно присваивать, и lvalue, которому нельзя.
---
Для класса вызов `operator=` — обычный вызов метода, поэтому prvalue класса присваивать можно, если оператор не помечен `&`. lvalue, которому нельзя присваивать, — например, const-объект.
```cpp
std::string("a") = "b";  // rvalue, вызывается operator=
const int c = 1;
c = 2;                   // ошибка: lvalue, но const
```
Подвох: для встроенных типов prvalue присваивать нельзя (`1 = 2` — ошибка); lvalue — имя массива — тоже не присваивается. Категория значения и возможность присваивания — независимые свойства.
См.: language/value_category, language/operators

## cpp-c-0502 · cpp-t-062
К чему привязывается неконстантная lvalue-ссылка `T&`, а к чему — rvalue-ссылка `T&&`?
---
`T&` привязывается к lvalue типа `T`; `T&&` — к rvalue (prvalue или xvalue), но не к lvalue. Обе — псевдонимы существующего объекта: инициализируются при объявлении и не переназначаются. Rvalue-ссылка, привязанная к prvalue, продлевает жизнь временного объекта.
Подвох: имя rvalue-ссылки — lvalue, поэтому `int&& r = 1; int&& s = r;` — ошибка, нужен `std::move(r)`.
См.: language/reference

## cpp-c-0529 · cpp-t-062
Как ссылки взаимодействуют с `const` и категориями значений: что куда привязывается?
---
`const T&` привязывается к любым lvalue и rvalue (временный объект живёт, пока жива ссылка). `T&` не привязывается к rvalue, `T&&` — к lvalue. `const T&&` привязывается только к rvalue. Ссылка не отбрасывает `const`: `int&` к const-объекту привязать нельзя.
```cpp
int x = 1;
const int& a = 3;  // можно
int&& b = 2;       // можно
int&& c = x;       // ошибка: x — lvalue
int&& d = std::move(x);
```
Подвох: нельзя привязать `int&` к `const int` и `int&` к prvalue.
См.: language/reference

## cpp-c-0503 · cpp-t-063
Что такое forwarding reference и как `std::forward` сохраняет категорию аргумента?
---
Forwarding reference — параметр вида `T&&`, где `T` выводится для этой функции (или `auto&&`). Для lvalue выводится `T = U&`, и сворачивание ссылок даёт `U&`; для rvalue `T = U`, параметр — `U&&`. `std::forward<T>(x)` приводит `x` к `T&&`: lvalue остаётся lvalue, rvalue — rvalue.
```cpp
void g(int&);  void g(int&&);
template<class T> void f(T&& x) { g(std::forward<T>(x)); }
int i = 0;
f(i);  // T = int&,  вызывается g(int&)
f(1);  // T = int,   вызывается g(int&&)
```
Подвох: `const T&&` и `std::vector<T>&&` — обычные rvalue-ссылки; внутри `f` имя `x` — lvalue, без `forward` категория теряется.
См.: language/reference, utility/forward

## cpp-c-0518 · cpp-t-063
Как реализован `std::move` и почему у него именно такие принимаемый и возвращаемый типы?
---
```cpp
template<class T>
std::remove_reference_t<T>&& move(T&& x) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(x);
}
```
Параметр `T&&` — forwarding reference, чтобы принять и lvalue (`T = U&`), и rvalue. Возвращаемый тип — `U&&` после `remove_reference`: без него при `T = U&` свернулось бы в `U&`. `move` только приводит к xvalue и ничего не перемещает.
Подвох: `std::move(const_obj)` даёт `const U&&`, и выбирается конструктор копирования.
См.: utility/move

## cpp-c-0504 · cpp-t-064
Как `decltype` определяет тип выражения `e`?
---
Если `e` — имя без скобок или доступ к члену без скобок, `decltype(e)` даёт объявленный тип сущности. Иначе для lvalue получается `T&`, для xvalue — `T&&`, для prvalue — `T`, где `T` — тип выражения.
```cpp
int i = 0;
decltype(i)     a = i;  // int
decltype((i))   b = i;  // int&
decltype(i + 1) c = 0;  // int, prvalue
```
Подвох: скобки вокруг имени превращают его в lvalue-выражение и меняют результат; выражение под `decltype` не вычисляется.
См.: language/decltype

## cpp-c-0530 · cpp-t-064
Что делает `decltype(auto)` и когда он нужен?
---
`decltype(auto)` выводит тип по правилам `decltype` от инициализатора или возвращаемого выражения, а не по правилам `auto` (которые отбрасывают ссылки и `const`). Нужен, чтобы точно сохранить тип, включая ссылку, например при возврате результата другой функции или `operator[]`.
```cpp
int i = 0;
int& f() { return i; }
decltype(auto) g() { return f(); }  // int&
auto h() { return f(); }            // int
```
Подвох: `return (x);` для локальной `x` даёт `int&` на уничтоженный объект — висячая ссылка. Доступно с C++14.
См.: language/auto, language/decltype

## cpp-c-0505 · cpp-t-065
Каков выбор `std::move_if_noexcept(x)` и зачем он нужен при реаллокации контейнера?
---
Возвращает `T&&`, если `T` nothrow-перемещаем или не копируем; иначе возвращает `const T&`, то есть выбирается копирование. Так, `std::vector::resize` при реаллокации выбирает между перемещением и копированием: при исключении всё откатывается, что возможно только если не перемещали бросающим конструктором (строгая гарантия).
Подвох: если перемещение бросает и копирования нет, вектор всё равно перемещает, а гарантия исключений теряется — состояние не определено. Поэтому перемещающие операции помечают `noexcept`.
См.: utility/move_if_noexcept, language/move_constructor

## cpp-c-0519 · cpp-t-065
Почему при реаллокации вектора нельзя просто скопировать память через `std::memcpy`?
---
`memcpy` побайтово копирует объекты, не вызывая конструкторов и деструкторов. Для типов, не являющихся trivially copyable, поведение не определено: копия владеющего типа даёт двойное освобождение ресурса, а объект с указателем на собственное поле (например, строка с малой буферной оптимизацией) после копирования указывает на старую память.
Подвох: `memcpy` допустим только для trivially copyable типов. [не по cppreference]
См.: string/byte/memcpy, types/is_trivially_copyable

## cpp-c-0506 · cpp-t-066
Как устроено совместное владение объектом в `std::shared_ptr`?
---
Несколько `shared_ptr` владеют одним объектом; он уничтожается (удалителем или `delete`), когда последний владелец уничтожен или переназначен через `operator=`/`reset()`. Обычно владельцы делят блок управления со счётчиками сильных и слабых ссылок и удалителем. [не по cppreference]
Подвох: вызов методов на разных `shared_ptr` (даже копиях одного объекта) потокобезопасен, на одном и том же `shared_ptr` из нескольких потоков при записи — гонка данных; два `shared_ptr` из одного сырого указателя дважды удалят объект.
См.: memory/shared_ptr

## cpp-c-0520 · cpp-t-066
Какие проблемы решают `make_shared` и `make_unique`?
---
Они создают объект и сразу владеющий им указатель без явного `new`. `make_shared` делает одно выделение памяти под объект и блок управления; обе функции исключаются из ситуации, когда при `f(shared_ptr<T>(new T), g())` до C++17 исключение из `g` могло привести к утечке.
```cpp
auto p = std::make_shared<std::string>(3, 'a');  // "aaa"
auto u = std::make_unique<int[]>(5);              // пять нулей
```
Подвох: память под объект при `make_shared` освобождается только после обнуления и слабых ссылок; нельзя задать свой удалитель. [не по cppreference]
См.: memory/shared_ptr/make_shared, memory/unique_ptr/make_unique

## cpp-c-0507 · cpp-t-067
Что меняет `mutable` в лямбда-выражении с захватом по значению?
---
Без `mutable` оператор вызова лямбды `const`, и копии, захваченные по значению, изменять нельзя. С `mutable` оператор вызова не `const`, копии можно менять; исходные переменные не затрагиваются.
```cpp
int n = 0;
auto f = [n]() mutable { return ++n; };
f(); f();  // возвращают 1, 2; внешняя n == 0
```
Подвох: изменения сохраняются между вызовами, так как копия — поле замыкания; копия замыкания получит копию состояния. Без `mutable` `++n` — ошибка компиляции.
См.: language/lambda

## cpp-c-0521 · cpp-t-067
Как захватить объект перемещением и как захватить по константной ссылке?
---
Через захват с инициализацией (C++14): `[имя = выражение]` создаёт поле замыкания, инициализируемое выражением. Перемещение: `[q = std::move(p)]`. Константная ссылка: `[&r = std::as_const(x)]`.
```cpp
auto p = std::make_unique<int>(1);
auto f = [q = std::move(p)] { return *q; };
int x = 0;
auto g = [&r = std::as_const(x)] { return r; };
```
Подвох: замыкание с move-only захватом не копируется; захват пачки — `[...xs = std::move(xs)]` (C++20). По умолчанию `[&]`/`[=]` легко дают висячую ссылку или неявный захват `this`.
См.: language/lambda

## cpp-c-0508 · cpp-t-068
Что означает SFINAE при подстановке аргументов шаблона?
---
Substitution Failure Is Not An Error: если подстановка выведенных или явных аргументов даёт некорректный тип или выражение в непосредственном контексте, этот кандидат отбрасывается из набора перегрузок, а не вызывает ошибку компиляции. Это позволяет выбирать перегрузки по свойствам типов.
Подвох: ошибка внутри тела функции или в определении вложенного шаблона — не непосредственный контекст, она остаётся жёсткой ошибкой; если подходящих кандидатов не осталось, ошибка есть. С C++20 то же чаще выражают через concepts.
См.: language/sfinae

## cpp-c-0528 · cpp-t-068
Как устроен `std::enable_if` и как его применяют для SFINAE?
---
```cpp
template<bool B, class T = void> struct enable_if {};
template<class T> struct enable_if<true, T> { using type = T; };
```
При `B == false` вложенного `type` нет, обращение `enable_if_t<...>` в сигнатуре шаблона даёт SFINAE-ошибку и кандидат отбрасывается. Пример: `template<class T> std::enable_if_t<std::is_integral_v<T>, T> half(T x)` участвует в перегрузке только для целых типов.
Подвох: две перегрузки с разным `enable_if` только в аргументе по умолчанию шаблона считаются одной сигнатурой — переносите условие в возвращаемый тип или параметр.
См.: types/enable_if, language/sfinae

## cpp-c-0509 · cpp-t-069
Что задаёт ограничение `requires` у шаблона C++20?
---
Ограничение — условие на шаблонные аргументы, проверяемое при подстановке: если оно ложно, кандидат не подходит. Записывается как requires-clause (`requires C<T>`) после списка параметров, через `concept` или сокращённо (`C auto x`). `requires { ... }` — выражение-prvalue `bool`, проверяющее корректность выражений и типов.
Подвох: атомарное ограничение должно быть именно `bool`; сложное выражение в requires-clause нужно брать в скобки (`requires (N > 0)`). Более ограниченный шаблон предпочитается при выборе перегрузки.
См.: language/requires, language/constraints

## cpp-c-0522 · cpp-t-069
Какие четыре вида требований бывают в requires-выражении?
---
Простое (выражение должно быть корректно), типовое (`typename T::X`), составное (`{ expr } -> concept`, может проверять `noexcept` и тип результата) и вложенное (`requires cond;` — условие должно быть истинным).
```cpp
template<class T> concept C = requires(T a, T b) {
    a + b;                                // простое
    { a + b } -> std::convertible_to<T>;  // составное
    typename T::value_type;               // типовое
    requires sizeof(T) <= 16;             // вложенное
};
```
Подвох: без вложенного `requires` выражение `sizeof(T) <= 16` лишь проверяется на корректность, а не на истинность.
См.: language/requires

## cpp-c-0510 · cpp-t-070
Для чего предназначен `std::function<R(Args...)>`?
---
Копируемая обёртка, хранящая любой вызываемый объект с подходящей сигнатурой: указатель на функцию, функциональный объект, замыкание, указатель на член. Позволяет хранить и передавать их единым типом `R(Args...)`.
Подвох: вызов пустой обёртки бросает `std::bad_function_call`; проверка — `if (f)`. Хранимый объект должен быть копируемым, поэтому move-only лямбда не помещается (для этого `std::move_only_function`, C++23).
См.: utility/functional/function

## cpp-c-0527 · cpp-t-070
Что делает `std::bind` и как им пользоваться?
---
`std::bind(f, args...)` возвращает вызываемый объект, связывающий часть аргументов `f` с заданными значениями; `std::placeholders::_1, _2…` обозначают аргументы будущего вызова.
```cpp
int sub(int a, int b) { return a - b; }
auto f = std::bind(sub, std::placeholders::_1, 10);
int r = f(25);  // sub(25, 10) == 15
```
Подвох: связанные аргументы копируются, для ссылок нужны `std::ref`/`std::cref`; обычно проще лямбда.
См.: utility/functional/bind

## cpp-c-0511 · cpp-t-071
Как прочитать тип `int (*(*)())()`?
---
Читают от места имени (здесь его нет) изнутри наружу: `(*)` — указатель на функцию без параметров `()`, которая возвращает `*` — указатель на функцию без параметров, возвращающую `int`. Итого: указатель на функцию без параметров, возвращающую указатель на функцию без параметров, возвращающую `int`.
```cpp
using Fn = int();
Fn* (*p)();  // то же, что int (*(*p)())()
```
Подвох: постфиксные `[]` и `()` связываются сильнее `*`, поэтому скобки вокруг `*` обязательны; `using` упрощает чтение. [не по cppreference]
См.: language/pointer, language/declarations

## cpp-c-0523 · cpp-t-071
Можно ли объявить ссылку на массив и ссылку на функцию?
---
Можно: ссылка на массив сохраняет размер, ссылка на функцию — привязывается к функции.
```cpp
int a[3];
int (&ra)[3] = a;     // ссылка на массив
void g(int);
void (&rg)(int) = g;  // ссылка на функцию
```
Подвох: скобки обязательны (`int& ra[3]` — массив ссылок, а он запрещён). Нельзя также объявить указатель на ссылку, ссылку на ссылку (кроме через typedef/шаблон) и ссылку на `void`. [не по cppreference: синтаксис ссылок на массив и функцию]
См.: language/reference, language/pointer

## cpp-c-0512 · cpp-t-072
Как объявить указатель на поле и указатель на метод класса `C`?
---
Указатель на поле типа `T`: `T C::*`; указатель на метод: `R (C::*)(Args...)` (для const-метода — с `const` после списка). Применяют операторы `.*` и `->*`.
```cpp
struct C { int x; int f(int a) { return a; } };
int C::* pf = &C::x;
int (C::* pm)(int) = &C::f;
C obj{1}; C* ptr = &obj;
obj.*pf = 2;  int r = (ptr->*pm)(3);
```
Подвох: вызов метода через указатель пишут как `(obj.*pm)(args)` в скобках; указатель на член образует только выражение `&C::m` ровно в таком виде (`&(C::m)` не подходит). С `std::function` и `std::bind` такой указатель работает по правилам INVOKE: `std::function<int(C&, int)> g = &C::f;` — первым аргументом передают объект.
См.: language/pointer, language/operator_member_access, utility/functional

## cpp-c-0524 · cpp-t-072
Почему `sizeof` указателя на метод отличается от `sizeof` обычного указателя?
---
Указатель на метод в Itanium ABI (GCC, Clang) занимает два слова: первое — адрес функции или (для виртуального метода) смещение в vtable, второе — поправка к `this` для множественного наследования. [не по cppreference]
```cpp
struct C { void f(); };
static_assert(sizeof(&C::f) == 2 * sizeof(void*));  // Itanium ABI
```
Подвох: размер зависит от ABI и компилятора; в стандарте он не задан.
См.: language/pointer

## cpp-c-0513 · cpp-t-073
Как защищённое наследование меняет доступ к унаследованным членам?
---
При `protected`-наследовании `public` и `protected` члены базы становятся `protected` в производном классе; `private` члены базы остаются недоступными. Членам и друзьям производного класса, а также его наследникам, доступны унаследованные protected-члены и преобразование `Derived*` в `Base*`.
```cpp
struct B { int a; };
struct D : protected B {};
D d;
d.a = 1;  // ошибка: a защищён в D
```
Подвох: снаружи нельзя неявно преобразовать `D*` в `B*`; `class` по умолчанию наследует `private`, `struct` — `public`.
См.: language/derived_class, language/access

## cpp-c-0525 · cpp-t-073
Как `friend` работает при наследовании?
---
Объявление `friend` даёт доступ к закрытым и защищённым членам того класса, где оно написано. Дружба не наследуется: друг базы не получает доступа к закрытым членам производного класса. [не по cppreference]
```cpp
class B { int p = 0; friend struct F; };
class D : public B { int q = 0; };
struct F {
    int g(B& b) { return b.p; }  // дружба с B
    int h(D& d) { return d.q; }  // ошибка: F не друг D
};
```
Подвох: друг-класс может сам наследоваться от закрытых и защищённых вложенных типов дружественного класса.
См.: language/friend, language/access

## cpp-c-0514 · cpp-t-074
Как виртуальное наследование решает ромбовидное наследование?
---
Если два промежуточных класса наследуют базу виртуально, наиболее производный объект содержит один общий подобъект этой базы, а не два. Конструктор виртуальной базы вызывает наиболее производный класс; инициализаторы базы в mem-init-списках промежуточных классов при этом игнорируются.
```cpp
struct A { int x; };
struct B : virtual A {};
struct C : virtual A {};
struct D : B, C {};  // один подобъект A; d.x однозначно
```
Подвох: если у базы нет конструктора по умолчанию, её должен явно инициализировать каждый наиболее производный класс.
См.: language/derived_class

## cpp-c-0526 · cpp-t-074
В каком порядке вызываются конструкторы при виртуальном наследовании?
---
Сначала конструируются виртуальные базы — в порядке обхода в глубину слева направо по объявлению прямых баз; затем невиртуальные прямые базы в порядке объявления; затем нестатические поля в порядке объявления; затем тело конструктора. Деструкторы вызываются в обратном порядке.
Подвох: виртуальную базу создаёт наиболее производный класс, поэтому она конструируется раньше невиртуальных баз, даже если объявлена позже.
См.: language/initializer_list, language/derived_class

## cpp-c-0515 · cpp-t-075
Почему нельзя задать универсальную схему расположения подобъектов и vtable при множественном и виртуальном наследовании?
---
Стандарт C++ не определяет расположение подобъектов, указателей на таблицы виртуальных функций, смещений или RTTI — это зависит от ABI. В Itanium ABI (GCC, Clang) полиморфный подобъект содержит vptr; в vtable перед адресами виртуальных функций лежат смещения до виртуальных баз, top offset (смещение до начала наиболее производного объекта) и указатель на `type_info`. [не по cppreference]
Подвох: число vptr зависит от структуры иерархии (не каждый базовый подобъект имеет свой); для виртуальных баз смещения хранятся в vtable и вычисляются во время выполнения.
См.: language/derived_class, language/virtual

## cpp-c-0701 · cpp-t-091
Как `enable_shared_from_this<T>` позволяет получить `shared_ptr` на уже управляемый объект?
---
Класс `T` публично наследуется от `std::enable_shared_from_this<T>`. Конструктор `shared_ptr` обнаруживает такую базу и записывает в её слабую ссылку `weak_this` контрольный блок первого владельца; `shared_from_this()` строит из неё новый `shared_ptr` с тем же блоком.
```cpp
struct A : std::enable_shared_from_this<A> {
    std::shared_ptr<A> self() { return shared_from_this(); }
};
auto p = std::make_shared<A>();
auto q = p->self(); // p.use_count() == 2
```
Подвох: вызов на объекте, не управляемом `shared_ptr` (в т.ч. в конструкторе), бросает `std::bad_weak_ptr` (до C++17 — UB); `shared_ptr<T>(this)` создаёт второй контрольный блок и ведёт к двойному удалению; наследование обязано быть публичным.
См.: memory/enable_shared_from_this

## cpp-c-0702 · cpp-t-091
Что такое CRTP?
---
CRTP — идиома, в которой класс `X` наследуется от шаблона `Y<X>`, то есть базе передаётся сам производный тип. Это даёт «статический полиморфизм»: база через `static_cast<Derived*>(this)` вызывает методы производного класса без виртуальных функций.
```cpp
template<class D> struct Base { void name() { static_cast<D*>(this)->impl(); } };
struct D1 : Base<D1> { void impl() {} };
```
Подвох: конструктор базы делают защищённым, чтобы нельзя было создать голый `Base` (создание такого объекта — UB). «Парадоксальное» наследование компилируется, потому что `Base<D1>` инстанцируется при неполном `D1`, а тела методов — позже, когда `D1` уже полон [не по cppreference].
См.: language/crtp

## cpp-c-0703 · cpp-t-092
В чём состоит type erasure в `std::any`?
---
`std::any` — типобезопасный контейнер одного значения любого копируемого типа (CopyConstructible), либо пустой. Конкретный тип `T` стирается из типа `any`: наружу виден один нешаблонный класс, а значение и операции над ним (копирование, уничтожение, `typeid`) скрыты за единым интерфейсом.
Подвох: в типичной реализации внутри лежит указатель на полиморфный внутренний класс-держатель `Holder<T> : HolderBase` с виртуальными `clone()` и деструктором; именно через них реализованы конструктор копирования и деструктор `any` [не по cppreference]. Реализациям разрешено хранить небольшие объекты без динамической аллокации (только для nothrow-move-constructible типов).
См.: utility/any

## cpp-c-0704 · cpp-t-092
Как проверить тип и извлечь значение из `std::any`?
---
`a.type()` возвращает `typeid` хранимого значения, `a.has_value()` проверяет непустоту. `std::any_cast<T>(a)` возвращает значение, а при несовпадении типа бросает `std::bad_any_cast`.
```cpp
std::any a = 1;
int i = std::any_cast<int>(a);       // 1
int* p = std::any_cast<int>(&a);     // указатель на значение
auto* f = std::any_cast<float>(&a);  // nullptr, без исключения
```
Подвох: приведение требует точного совпадения типа, без преобразований (`any_cast<float>` для `int` бросает исключение — пример cppreference); форма от указателя на `any` не бросает, а возвращает `nullptr` [не по cppreference].
См.: utility/any

## cpp-c-0705 · cpp-t-093
Как `shared_ptr` вызывает deleter нестандартного типа?
---
Deleter передаётся конструктору `shared_ptr(p, d)` и копируется в контрольный блок; тип deleter не входит в тип `shared_ptr<T>`. Когда счётчик владельцев падает до нуля, блок вызывает `d(p)` для управляемого указателя.
Подвох: deleter получает управляемый указатель, а не хранимый (разница видна при aliasing-конструкторе); достать deleter можно через `std::get_deleter<D>(sp)`. Стирание типа обеспечивает полиморфный контрольный блок-наследник, шаблонный по типу deleter [не по cppreference].
См.: memory/shared_ptr

## cpp-c-0706 · cpp-t-093
Для чего `std::allocate_shared` принимает аллокатор?
---
`std::allocate_shared<T>(alloc, args...)` создаёт объект типа `T` и `shared_ptr` на него, выделяя память под объект и контрольный блок через переданный аллокатор; объект конструируется аргументами `args...`. Как и `make_shared`, обычно делает одно выделение на объект и блок.
Подвох: контрольный блок хранит копию аллокатора (стирание его типа — тот же приём, что и для deleter) и освобождает память им же; при одном выделении память под объект освобождается лишь после исчезновения последнего `weak_ptr` [не по cppreference].
См.: memory/shared_ptr

## cpp-c-0707 · cpp-t-094
Как компилятор представляет лямбду без захватов?
---
Как уникальный безымянный тип замыкания (closure type) — класс с `operator()`, который по умолчанию `const`. Лямбда без захватов не имеет нестатических полей и неявно преобразуется в указатель на обычную функцию с той же сигнатурой.
```cpp
auto f = [](int x) { return x + 1; };
int (*p)(int) = f;          // неявное преобразование
auto g = +f;                // «positive lambda hack»: g имеет тип int(*)(int)
```
Подвох: у каждой лямбды свой тип, даже при одинаковом теле; унарный `+` форсирует преобразование в указатель; default-конструктор и присваивание у лямбд без захватов есть только с C++20; `sizeof` пустого замыкания — как у пустого класса (обычно 1). Преобразование в указатель, правила конструкторов/присваивания и `sizeof` — [не по cppreference].
См.: language/lambda

## cpp-c-0708 · cpp-t-094
Как лямбда с захватом по значению хранит захваченное состояние?
---
Для каждого захваченного по значению объекта в типе замыкания заводится неименованное нестатическое поле, инициализированное в момент создания лямбды. `operator()` по умолчанию `const`, поэтому копии нельзя менять без `mutable`.
```cpp
int x = 1;
auto f = [x]() mutable { return ++x; };
f(); f();   // 2, затем 3; внешний x остаётся 1
```
Подвох: `sizeof` замыкания определяется захваченными полями (с выравниванием), для захвата по ссылке не определено, заводится ли поле; замыкание с захватами не приводится к указателю на функцию и не имеет default-конструктора. Наличие полей и их порядок, `sizeof` — [не по cppreference].
См.: language/lambda

## cpp-c-0709 · cpp-t-095
Для чего `std::invoke` нужен при реализации обобщённого вызова?
---
`std::invoke(f, args...)` (C++17) вызывает любой callable единообразно: функцию, функциональный объект, лямбду, указатель на метод или на поле, где первым аргументом идёт объект (ссылка, указатель или `reference_wrapper`). Обычный синтаксис `f(args...)` для указателей на члены не работает.
```cpp
struct S { int v = 7; int get(int k) const { return v + k; } };
S s;
int a = std::invoke(&S::get, s, 1); // 8
int b = std::invoke(&S::v, &s);     // 7
```
Подвох: для указателя на метод первый аргумент — объект, указатель на него или `reference_wrapper`; тип результата вычисляет `std::invoke_result_t` (`result_of` устарел в C++17 и удалён в C++20); `std::invoke_r` с заданным типом результата — C++23.
См.: utility/functional, types/result_of

## cpp-c-0710 · cpp-t-095
Что хранит `std::function<R(Args...)>`?
---
Копию произвольного вызываемого объекта (функция, лямбда, функтор, указатель на член), вызов которого возможен с аргументами `Args...` и даёт результат, приводимый к `R`. Цель должна быть копируемой; вызов пустого `function` бросает `std::bad_function_call`.
Подвох: `function` — копируемая обёртка; для move-only целей есть `std::move_only_function` (C++23), `std::copyable_function` (C++26) с квалификаторами в сигнатуре; тип цели стирается; `operator()` принимает параметры по значению, как в сигнатуре `R(Args...)`, и перенаправляет их цели; реализации обычно используют small buffer optimization — небольшой функтор хранится прямо внутри `function` без аллокации [не по cppreference].
См.: utility/functional

## cpp-c-0711 · cpp-t-096
Как SFINAE помогает реализовать `is_class`?
---
Две перегрузки: шаблон с параметром `int T::*` (указатель на член типа `T`) и запасная `...`. Для не-класса (`int`, указатель) тип `int T::*` некорректен, подстановка проваливается, первая перегрузка отбрасывается и выбирается запасная; для класса побеждает первая.
```cpp
template<class T> char test(int T::*);
template<class T> long test(...);
template<class T> constexpr bool is_cls = sizeof(test<T>(nullptr)) == 1;
```
Подвох: `std::is_class` — для не-union классов; в реализации cppreference первая перегрузка возвращает `integral_constant<bool, !is_union<T>::value>`, так что union отсекается через `is_union` (в билете этот случай опускают). Для неполного класса тоже `true`.
См.: language/sfinae, types/is_class

## cpp-c-0712 · cpp-t-096
Что означает SFINAE?
---
Substitution Failure Is Not An Error: если при выводе или подстановке аргументов шаблона функции получается некорректный тип или выражение в непосредственном контексте, эта специализация молча исключается из набора кандидатов, а ошибки нет.
```cpp
template<class T> auto f(T t) -> decltype(t.size()) { return t.size(); }
int f(...) { return -1; }
f(5); // первая отброшена, выбрана вторая
```
Подвох: работает только для «непосредственного контекста» (заголовок: параметры, возвращаемый тип, шаблонные аргументы); ошибка внутри тела функции или при инстанцировании вложенного шаблона — обычная ошибка компиляции. `std::enable_if` и концепты (C++20) используют тот же механизм.
См.: language/sfinae, types/enable_if

## cpp-c-0721 · cpp-t-096
Что такое comma trick в SFINAE и зачем он нужен?
---
Через оператор «запятая» в `decltype` проверяют допустимость выражения, но тип результата подменяют своим: `decltype(expr, void(), std::true_type{})` корректно, только если `expr` корректно, а его тип — `std::true_type`.
```cpp
template<class T>
auto has_size(int) -> decltype(std::declval<T>().size(), std::true_type{});
template<class T> std::false_type has_size(...);
```
Подвох: `operator,` можно перегрузить, поэтому левый операнд приводят к `void`: `(expr, void(), X{})`; иначе возврат типа `expr` (например, `void`) сломал бы тип результата [не по cppreference].
См.: language/operator_other, language/sfinae

## cpp-c-0722 · cpp-t-096
Как реализовать `is_polymorphic`?
---
Класс полиморфен, если у него есть хотя бы одна виртуальная функция (своя или унаследованная). Через SFINAE: `dynamic_cast<const volatile void*>(declval<T*>())` корректен только для полиморфного `T`, иначе перегрузка отбрасывается.
```cpp
template<class T> char t(decltype(dynamic_cast<const volatile void*>(std::declval<T*>())));
template<class T> long t(...);
template<class T> constexpr bool poly = sizeof(t<T>(nullptr)) == 1;
```
Подвох: `std::is_polymorphic` истинен только для не-union классов; для неполного не-union класса поведение не определено; наследование без `virtual` (даже виртуальное наследование от базы без виртуальных функций) полиморфизма не даёт. Реализация cppreference использует ровно этот `dynamic_cast` с `static_cast<T*>(nullptr)`.
См.: types/is_polymorphic

## cpp-c-0713 · cpp-t-097
Для чего предназначена `std::declval<T>()`?
---
`std::declval<T>()` возвращает `T&&` (для `T&` — `T&`; для `void` — `void`), то есть позволяет в невычисляемом контексте (`decltype`, `sizeof`, `noexcept`) использовать выражение типа `T`, даже если у `T` нет доступного конструктора или он неполный.
```cpp
struct A { A() = delete; int f(); };
using R = decltype(std::declval<A>().f()); // int
```
Подвох: `declval<T>()` — xvalue, а `declval<T&>()` — lvalue, поэтому от выбора `T` зависит, какая перегрузка метода будет выбрана; основа для `is_constructible`, `is_convertible`, `is_assignable` и проверки наличия метода.
См.: utility/declval

## cpp-c-0714 · cpp-t-097
Можно ли вызывать `std::declval` во время выполнения?
---
Нет. Функция объявлена, но не определена; её использование в вычисляемом выражении (odr-use) делает программу некорректной (в реализациях — `static_assert` при инстанцировании).
```cpp
using T1 = decltype(std::declval<int>() + 1); // ок
int x = std::declval<int>();                  // ошибка
```
Подвох: внутри `decltype`, `sizeof`, `noexcept` и `typeid` (для не-полиморфных типов) выражение не вычисляется, поэтому `declval` разрешена.
См.: utility/declval

## cpp-c-0723 · cpp-t-097
Как проверить наличие метода в классе через SFINAE?
---
Пишут две перегрузки: первая использует в `decltype` выражение вызова метода на `std::declval<T>()` и возвращает/принимает `true_type`; вторая — запасная с `...`. Если выражение некорректно, первая отбрасывается и срабатывает вторая.
```cpp
template<class T> auto has_foo(int) -> decltype(std::declval<T&>().foo(), std::true_type{});
template<class T> std::false_type has_foo(...);
constexpr bool b = decltype(has_foo<A>(0))::value;
```
Подвох: аргумент `0` (`int`) заставляет предпочесть первую перегрузку перед `...`; проверка находит и унаследованные методы, а приватный метод даёт `false`, так как доступ проверяется при подстановке. В C++20 проще написать `requires`.
См.: language/sfinae, utility/declval

## cpp-c-0715 · cpp-t-098
Какова цель `std::is_base_of<Base, Derived>`?
---
`std::is_base_of<Base, Derived>::value` равен `true`, если `Base` — прямая или непрямая база `Derived`, либо оба типа — один и тот же не-union класс (без учёта cv); для неоднозначной, приватной и защищённой базы тоже `true`.
Подвох: оба типа должны быть классами, не union (иначе `false`); если типы разные и оба классы, `Derived` обязан быть полным, иначе UB; `is_base_of<Base, Base>` — `true`, а `is_base_of<int, int>` — `false`.
См.: types/is_base_of

## cpp-c-0716 · cpp-t-098
Почему проверка неявного преобразования `Derived*` в `Base*` не подходит для `is_base_of`?
---
Такое преобразование недоступно при приватном или защищённом наследовании, а при неоднозначной базе (повторяется несколько раз) — некорректно. Поэтому по `is_convertible<Derived*, Base*>` нельзя отличить «не база» от «база, но недоступная»: в обоих случаях `false`.
```cpp
struct B {};
struct D : private B {};
// is_convertible_v<D*, B*> == false, но is_base_of_v<B, D> == true
```
Подвох: `is_convertible` учитывает доступность, а `is_base_of` — только факт наследования; cppreference замечает, что во многих ситуациях `is_convertible<B*, A*>` как раз более подходящая проверка. Решение — перегрузки с запасным `(...)` (см. следующую карточку).
См.: types/is_base_of, types/is_convertible

## cpp-c-0724 · cpp-t-098
Как реализуется `is_base_of`, чтобы работало и с приватным наследованием?
---
Через две перегрузки по преобразованию `D*` в `const volatile B*`: `test_ptr_conv(const volatile B*)` даёт `true_type`, запасная `(const volatile void*)` — `false_type`. Обёртка `test_is_base_of<B, D>(int)` вызывает их с `static_cast<D*>(nullptr)`, а запасная `(...)` возвращает `true_type`. Итог дополнительно требует, чтобы `B` и `D` были классами.
Подвох: для приватной или неоднозначной базы выбор перегрузки или проверка доступа проваливает подстановку в `decltype`, срабатывает `(...)` и результат `true` — на этом и держится отличие от `is_convertible`. Для неродственных классов выбирается `void*`-перегрузка и результат `false`.
См.: types/is_base_of

## cpp-c-0717 · cpp-t-099
Как определяется концепт в C++20?
---
Концепт — именованный компилятор-вычисляемый предикат над шаблонными параметрами: `template<class T> concept Name = constraint-expression;`. Результат — константное `bool`-значение, которое используется как ограничение.
```cpp
template<class T>
concept Addable = requires(T a, T b) { a + b; };
```
Подвох: определение концепта должно быть на уровне пространства имён; его нельзя специализировать или инстанцировать явно, нельзя ограничить (`template<C T> concept …` — ошибка) и нельзя сделать рекурсивным; стандартные концепты лежат в `<concepts>`.
См.: language/constraints, concepts

## cpp-c-0718 · cpp-t-099
Что даёт ограничение шаблона концептом?
---
Оно задаёт требования к аргументам и влияет на выбор перегрузки: шаблон с невыполненными ограничениями не участвует в разрешении перегрузки, а при нескольких подходящих выигрывает более ограниченный. Формы записи: `template<C T>`, `requires C<T>` и сокращённая `void f(C auto x)`.
```cpp
template<std::integral T> T twice(T x) { return x * 2; }
void g(std::floating_point auto y); // сокращённый синтаксис
```
Подвох: `auto` в параметре функции делает её шаблоном (C++20); при нарушении ограничения сообщение об ошибке указывает на конкретный концепт, а не на глубокий инстанцированный код.
См.: language/constraints

## cpp-c-0725 · cpp-t-099
Как выбирается перегрузка, если одно ограничение строже другого (subsumption)?
---
Ограничения нормализуются в атомарные ограничения, соединённые `&&` и `||`; ограничение A включает B (subsumes), если из A логически следует B. Если остальные критерии равны, выигрывает более ограниченная перегрузка (частичный порядок).
```cpp
template<std::integral T> void f(T);        // 1
template<std::signed_integral T> void f(T); // 2
f(1); // выбрана 2: signed_integral = integral && is_signed
```
Подвох: атомарные ограничения считаются одинаковыми, только если это одно и то же выражение в одном месте исходника; два отдельно написанных `sizeof(T) > 1` не включают друг друга, и вызов станет неоднозначным [не по cppreference]. Из вырезки: `same_as<T, U>` включает `same_as<U, T>` и наоборот.
См.: language/constraints

## cpp-c-0726 · cpp-t-099
Как реализовать `advance` для разных категорий итераторов с помощью концептов?
---
Пишут перегрузки, ограниченные концептами итераторов; `std::random_access_iterator` включает `bidirectional_iterator` и `input_iterator`, поэтому для самого сильного итератора выбирается самая специализированная версия.
```cpp
template<std::input_iterator It>
void adv(It& it, int n) { while (n-- > 0) ++it; }
template<std::random_access_iterator It>
void adv(It& it, int n) { it += n; }
```
Подвох: для двунаправленных итераторов нужна ещё перегрузка с обработкой `n < 0` через `--it`; без концептов то же делают тегами `iterator_category` и перегрузкой по тегу или `if constexpr`.
См.: iterator/advance, iterator/distance

## cpp-c-0719 · cpp-t-100
Когда выражение в `constexpr`-функции считается неопределённым поведением?
---
Если вычисление выражения приводит к UB (переполнение знакового, выход за границы массива, разыменование нулевого указателя), оно не является core constant expression, и в контексте, требующем константу, получается ошибка компиляции. Поэтому constexpr-вычисление — удобный способ поймать UB на этапе компиляции [не по cppreference: диагностика].
```cpp
constexpr int f(int x) { return 2147483647 + x; }
constexpr int a = f(1); // ошибка: переполнение не constant expression
```
Подвох: `constexpr` не превращает UB в определённое поведение: при вызове вне константного контекста UB остаётся обычным; если ни при каких аргументах вызов не может быть константным, программа некорректна, диагностика не требуется (NDR, до C++23).
См.: language/ub, language/constexpr

## cpp-c-0720 · cpp-t-100
Можно ли безусловно бросать исключения в `constexpr`-функции?
---
Нельзя: вычисление выражения `throw` не является constant expression. Функция с `throw` на некоторых путях остаётся допустимой `constexpr`, если при константном вычислении этот путь не выполняется.
```cpp
constexpr int checked(int x) {
    if (x < 0) throw "neg";
    return x;
}
constexpr int ok = checked(1); // ок; checked(-1) в constexpr — ошибка
```
Подвох: трюк используют как compile-time assert; в обычном вызове исключение работает как обычно. До C++26 `throw` в константном вычислении недопустим вовсе; с C++26 неперехваченное исключение по-прежнему делает выражение не constant expression.
См.: language/constexpr

## cpp-c-0727 · cpp-t-100
Можно ли использовать `new`/`delete` в `constexpr`-функциях?
---
С C++20 можно: константное вычисление может выделить память через `new`, но обязано освободить её до конца вычисления (transient allocation); утечка или возврат выделенной памяти наружу в константное значение делают выражение не constant expression.
```cpp
constexpr int sum() {
    int* p = new int[3]{1, 2, 3};
    int s = p[0] + p[1] + p[2];
    delete[] p;
    return s; // 6
}
static_assert(sum() == 6);
```
Подвох: constexpr-`std::vector`/`std::string` в C++20 стали возможны благодаря этому; результат нельзя оставить указывающим на ещё живую динамическую память. Правило: выделенную в вычислении память нужно освободить в нём же (constant_expression).
См.: language/constexpr, language/constant_expression

## cpp-c-0728 · cpp-t-100
Чем `consteval` отличается от `constexpr`?
---
`consteval` (C++20) делает функцию immediate function: каждый её вызов обязан давать constant expression, иначе программа некорректна. `constexpr` же допускает выполнение и во время исполнения.
```cpp
consteval int sq(int x) { return x * x; }
constexpr int a = sq(4); // ок
int n = 3;
int b = sq(n);           // ошибка: n не константа
```
Подвох: `consteval` подразумевает `inline`, не применяется к деструкторам и функциям выделения/освобождения памяти; взять адрес immediate function можно только внутри константного выражения.
См.: language/consteval

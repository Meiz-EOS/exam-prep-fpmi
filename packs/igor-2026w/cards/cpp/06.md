## cpp-c-0601 · cpp-t-076
На какой тип динамической диспетчеризации ограничен виртуальный вызов из конструктора или деструктора?
---
Во время работы конструктора или деструктора класса `X` динамический тип объекта — `X`, поэтому виртуальный вызов выбирает финальный переопределитель в `X` или его базах; переопределения из более производных классов не вызываются. То же верно для вызова из списка инициализации.
```cpp
struct B { B() { f(); } virtual void f() { /* B::f */ } };
struct D : B { void f() override { /* не вызывается из B() */ } };
```
Подвох: поля `D` в этот момент ещё не построены, поэтому вызов `D::f` был бы опасен.
См.: language/virtual

## cpp-c-0602 · cpp-t-076
Что важно о чисто виртуальном вызове из конструктора или деструктора?
---
Виртуальный вызов чисто виртуальной функции из конструктора или деструктора абстрактного класса — неопределённое поведение, независимо от того, есть ли у функции определение. На практике это аварийное завершение с сообщением «pure virtual method called» (GCC/Clang) [не по cppreference].
Подвох: определение чисто виртуальной функции пишут вне класса (у деструктора оно обязательно) и вызывают квалифицированным именем `B::f()`; квалифицированный вызов виртуальным не является.
См.: language/abstract_class, language/virtual

## cpp-c-0603 · cpp-t-076
Какие значения аргументов по умолчанию применяются при виртуальном вызове?
---
Тело функции выбирается по динамическому типу, а аргументы по умолчанию берутся из объявления, найденного по статическому типу выражения; значения по умолчанию из переопределения игнорируются.
```cpp
struct B { virtual void f(int x = 1) { std::cout << x; } };
struct D : B { void f(int x = 2) override { std::cout << x; } };
D d; B& r = d; r.f(); // печатает 1: тело D::f, но x == 1
```
Подвох: поэтому в переопределениях аргументы по умолчанию не меняют.
См.: language/default_arguments, language/virtual

## cpp-c-0635 · cpp-t-076
Могут ли виртуальные функции быть шаблонными?
---
Нет: шаблон функции-члена не может быть виртуальным. Причина: набор виртуальных функций класса должен быть известен при определении класса (размер таблицы виртуальных функций), а шаблон мог бы порождать неограниченное число специализаций [не по cppreference].
Подвох: обходные пути — виртуальная функция фиксированной сигнатуры, вызывающая шаблонный помощник, либо стирание типа. Невиртуальная неопределённая функция даёт ошибку линковки, а не компиляции.
См.: language/member_template

## cpp-c-0604 · cpp-t-077
Как объявляют шаблонный параметр-шаблон?
---
Параметр-шаблон принимает шаблон класса: `template<class T, template<class...> class Cont = std::vector> class Stack { Cont<T> data; };`. Использование: `Stack<int>` или `Stack<int, std::deque>`.
Подвох: до C++17 в объявлении самого параметра-шаблона нужно слово `class`, с C++17 допустимо и `typename`; шаблон-аргумент должен подходить по списку параметров (поэтому `template<class...> class` принимает `vector<T, Alloc>`).
См.: language/template_parameters

## cpp-c-0605 · cpp-t-077
Почему аллокатор не является шаблонным шаблонным параметром `allocator_traits`?
---
Аллокатором может быть любой тип, а не только экземпляр шаблона с одним типовым параметром: класс без параметров, `Pool<T, N>` с нетиповым параметром. Шаблонный шаблонный параметр такие типы не принял бы, поэтому `allocator_traits<Alloc>` и контейнеры берут готовый тип `Alloc` [не по cppreference].
Подвох: аллокатор для другого `T` получают через `rebind_alloc`: это `Alloc::rebind<T>::other` либо `A<T, Args...>` для `A<U, Args...>`, где `Args` — только типы.
См.: memory/allocator_traits, language/template_parameters

## cpp-c-0606 · cpp-t-077
Как обратиться к шаблону-члену зависимого типа?
---
Если имя до `.`, `->` или `::` зависит от параметра шаблона, перед именем члена-шаблона нужно написать `template`, иначе `<` разбирается как оператор сравнения; для вложенных типов — `typename`.
```cpp
template<class T> void g(T& obj) {
    obj.template f<int>();
    typename T::value_type v{};
}
```
Подвох: `template` нужен только для зависимых имён и только перед именем шаблона.
См.: language/dependent_name

## cpp-c-0636 · cpp-t-077
Почему в шаблонном наследнике нельзя просто написать имя поля шаблонного родителя?
---
В определении шаблона не раскрываются имена из зависимой базы (`B<T>`: она может быть специализирована), поэтому неквалифицированное `x` не находится. Помогают `this->x`, `B<T>::x` или `using B<T>::x;`.
```cpp
template<class T> struct B { int x = 0; };
template<class T> struct D : B<T> { int get() { return this->x; } }; // голое `x` — ошибка
```
Подвох: для методов базы то же правило.
См.: language/dependent_name

## cpp-c-0607 · cpp-t-078
Какие четыре формы свёртки параметров существуют?
---
Унарная правая `(E op ...)` → `E1 op (... op (EN-1 op EN))`; унарная левая `(... op E)` → `((E1 op E2) op ...) op EN`; бинарная правая `(E op ... op I)`; бинарная левая `(I op ... op E)`, где `I` — начальное значение; оператор в бинарной форме один и тот же.
Подвох: для неассоциативных операторов форма важна: при `1, 2, 3` выражение `(args - ...)` равно 2, а `(... - args)` равно −4; скобки — часть синтаксиса.
См.: language/fold

## cpp-c-0608 · cpp-t-078
Что происходит при свёртке пустого пакета?
---
Бинарная свёртка при пустом пакете даёт начальное значение `I`. Унарная допустима только для `&&` (результат `true`), `||` (`false`) и `,` (`void()`); для остальных операторов пустая унарная свёртка некорректна.
```cpp
template<class... T> bool any(T... a) { return (... || a); } // any() == false
```
Подвох: `(args + ...)` для пустого пакета не компилируется; нужно `(args + ... + 0)`.
См.: language/fold

## cpp-c-0609 · cpp-t-078
Как проверить сверткой, что все значения пакета истинны?
---
Унарной свёрткой по `&&`; для пустого пакета результат `true`, вычисление короткое — слева направо.
```cpp
template<class... T> bool all(T... a) { return (... && a); }
// all() == true; all(true, false) == false
```
Подвох: для типа с перегруженным `&&` короткое вычисление пропадает; элементы должны приводиться к `bool`.
См.: language/fold

## cpp-c-0637 · cpp-t-078
Как написать `print` от переменного числа аргументов и проверку «все типы пакета одинаковы» свёрткой?
---
`print`: запятая в качестве оператора свёртки. «Все одинаковы»: свёртка `&&` по `is_same`.
```cpp
template<class... Ts> void print(const Ts&... a) { ((std::cout << a << ' '), ...); }
template<class T, class... Ts>
constexpr bool all_same = (std::is_same_v<T, Ts> && ...);
```
Подвох: `(std::cout << ... << a)` (бинарная левая) печатает без разделителей; для `all_same` с пустым `Ts` результат `true`.
См.: language/fold

## cpp-c-0610 · cpp-t-079
Как работают `std::back_inserter` и `std::inserter`?
---
`back_inserter(c)` возвращает `back_insert_iterator`, `inserter(c, it)` — `insert_iterator`. При присваивании (даже без разыменования) первый вызывает `c.push_back(v)`, второй — `c.insert(позиция, v)`; `*it` и `++it` ничего не делают.
```cpp
std::vector<int> v;
std::generate_n(std::back_inserter(v), 3, [n = 0]() mutable { return ++n; }); // 1 2 3
```
Подвох: `insert_iterator` вставляет перед сохранённой позицией, поэтому порядок вставляемых элементов сохраняется; `back_inserter` требует `push_back`.
См.: iterator/back_insert_iterator, iterator/insert_iterator

## cpp-c-0611 · cpp-t-079
Каково назначение `std::istream_iterator` и `std::ostream_iterator`?
---
`istream_iterator<T>` — однопроходный входной итератор: значение читается через `operator>>` при продвижении (`++`), первое — при конструировании; `*` возвращает копию последнего прочитанного. Итератор по умолчанию — конец потока. `ostream_iterator<T>(os, delim)` при присваивании пишет значение через `operator<<`, затем разделитель; `*`, `++` — no-op.
```cpp
std::copy(std::istream_iterator<int>(std::cin), std::istream_iterator<int>(),
          std::ostream_iterator<int>(std::cout, " "));
```
Подвох: разыменование или продвижение итератора конца потока — UB; `T` должен быть DefaultConstructible, CopyConstructible, CopyAssignable.
См.: iterator/istream_iterator, iterator/ostream_iterator

## cpp-c-0638 · cpp-t-079
Что такое `std::istringstream` и `std::ostringstream`?
---
Потоки над строкой в памяти: `istringstream` читает из заданной `std::string` обычным `operator>>`, `ostringstream` накапливает вывод через `operator<<`, результат даёт `str()`.
```cpp
std::istringstream in("1 2 3"); int a, b; in >> a >> b; // 1, 2
std::ostringstream out; out << a << '-' << b; // out.str() == "1-2"
```
Подвох: `str()` возвращает копию, а не ссылку.
См.: io/basic_istringstream, io/basic_ostringstream

## cpp-c-0612 · cpp-t-080
Как устроена стандартная `std::unordered_map` на уровне абстракции?
---
Элементы не упорядочены и разложены по корзинам: хеш ключа определяет корзину, равенство ключей ищет внутри неё. Интерфейс (корзины, `local_iterator`, `bucket_count`) фактически требует цепочек (раздельное связывание).
Подвох: «вектор списков» плох — итератор `++` обязан перескакивать пустые корзины (не O(1)); поэтому реализации держат один односвязный список всех узлов, корзина указывает на узел перед своим первым. Хеш часто кешируют в узле, чтобы быстрее делать rehash и сравнивать [не по cppreference].
См.: container/unordered_map

## cpp-c-0613 · cpp-t-080
Что инвалидирует `rehash` в `std::unordered_map`?
---
`rehash`, `reserve`, `clear`, `operator=` инвалидируют все итераторы; `insert`, `emplace`, `operator[]` — только если вызвали rehash; `erase` — только итераторы на удалённый элемент; чтение — никогда; `swap` сохраняет итераторы и ссылки, но инвалидирует `end()`.
Подвох: ссылки и указатели на элементы инвалидируются лишь удалением самого элемента, в том числе при rehash — они остаются действительными (в отличие от `vector`).
См.: container/unordered_map

## cpp-c-0614 · cpp-t-080
Какие требования накладываются на хеш-функцию `unordered_map`?
---
Если ключи эквивалентны по `KeyEqual`, `Hash` обязан давать для них одинаковое значение. Для своего ключа специализируют `std::hash` (оператор `const`, возвращает `size_t`) или передают `Hash` и `KeyEqual` параметрами шаблона.
```cpp
template<> struct std::hash<P> { size_t operator()(const P& p) const { return p.id; } };
```
Подвох: `operator==` ключа должен быть согласован с хешем, иначе элементы не находятся; специализации `std::hash` стандартной библиотеки не бросают исключений (кроме отдельных вроде `optional`, `variant`).
См.: container/unordered_map, utility/hash

## cpp-c-0639 · cpp-t-080
Что такое `load_factor` и что делает `rehash`?
---
`load_factor() = size() / bucket_count()`; если оно превышает `max_load_factor()`, контейнер автоматически увеличивает число корзин. `rehash(n)` меняет число корзин на значение не меньше `n` и не меньше `size() / max_load_factor()`, после чего элементы раскладываются по корзинам заново.
Подвох: в среднем линейно, в худшем квадратично; `rehash(0)` принудительно перестраивает таблицу. Идея реализации — перевесить существующие узлы без копирования элементов [не по cppreference]; итераторы при этом инвалидируются, ссылки — нет.
См.: container/unordered_map/rehash, container/unordered_map

## cpp-c-0615 · cpp-t-081
Какую гарантию при исключениях обычно дают операции стандартных контейнеров?
---
Вставка одного элемента при исключении не имеет эффекта (строгая гарантия): `vector::push_back`, `list::push_back`, одноэлементные `map::insert` и `unordered_map::insert`. Для `vector::insert` в середину эффекта нет, только если исключение выброшено не из копирования, перемещения или присваивания `T`.
Подвох: диапазонная вставка в `unordered_map` гарантий не даёт; `map::erase(iterator)` ничего не бросает.
См.: container/vector/push_back, container/list/push_back, container/map/insert, container/unordered_map/insert

## cpp-c-0616 · cpp-t-081
Почему перемещение элементов при реаллокации `std::vector` может ослабить гарантию исключений?
---
`vector` при реаллокации использует `std::move_if_noexcept`: перемещает, если move-конструктор `noexcept` или тип не копируется, иначе копирует (строгая гарантия сохраняется). Если `T` не копируется, его move бросает и исключение вылетело — гарантия снята, результат не определён.
Подвох: забытый `noexcept` на move-конструкторе заставляет `vector` копировать элементы при росте.
См.: container/vector/push_back, utility/move_if_noexcept

## cpp-c-0640 · cpp-t-081
Что будет, если `Compare` или `Hash` бросает исключение в `map` и `unordered_map`?
---
Для вставки одного элемента (`map::insert`, `unordered_map::insert` в одноэлементных формах) исключение из любой операции, включая `Compare` или `Hash`, оставляет контейнер без изменений (строгая гарантия): вставка не имеет эффекта.
Подвох: диапазонная вставка `unordered_map::insert(first, last)` гарантии не имеет.
См.: container/map/insert, container/unordered_map/insert

## cpp-c-0617 · cpp-t-082
Какова идея pool- и stack-аллокаторов?
---
Pool: заранее выделенный кусок делится на блоки одного размера, свободные блоки хранятся в списке; `allocate`/`deallocate` — O(1) без обращения к системе. Stack (arena): память выдаётся сдвигом указателя по буферу, `deallocate` обычно no-op или освобождает последний блок, весь буфер освобождается разом [не по cppreference].
Подвох: pool с фиксированным размером блока не подходит для `rebind` на тип другого размера.
См.: named_req/Allocator

## cpp-c-0618 · cpp-t-082
Для чего нужен `rebind_alloc`?
---
`std::allocator_traits<Alloc>::rebind_alloc<U>` даёт аллокатор для объектов типа `U`: `Alloc::rebind<U>::other`, если есть, иначе `A<U, Args...>` для `Alloc = A<T, Args...>`. Нужен контейнерам, выделяющим не `value_type`, а узлы: `list`, `map`, `set`, `unordered_*` [не по cppreference].
```cpp
using NodeAlloc = typename std::allocator_traits<Alloc>::template rebind_alloc<Node>;
```
Подвох: подстановка по умолчанию работает, только если `Args` — типы; для `Pool<T, N>` с нетиповым параметром нужен свой `rebind`.
См.: memory/allocator_traits

## cpp-c-0619 · cpp-t-083
Как аллокатор выбирается при копирующем конструировании allocator-aware контейнера?
---
Копирующий конструктор получает аллокатор от `std::allocator_traits<A>::select_on_container_copy_construction(a)`, где `a` — аллокатор копируемого контейнера: по возможности вызывается одноимённый член `a`, иначе возвращается `a` без изменений.
Подвох: move-конструктор перемещает аллокатор, остальные конструкторы принимают `const allocator_type&`.
См.: named_req/AllocatorAwareContainer, memory/allocator_traits/select_on_container_copy_construction

## cpp-c-0620 · cpp-t-083
Как `propagate_on_container_copy_assignment` влияет на копирующее присваивание?
---
Копирующее присваивание заменяет аллокатор цели аллокатором источника, только если `propagate_on_container_copy_assignment::value == true`; иначе аллокатор цели остаётся.
Подвох: по умолчанию в `allocator_traits` значение `std::false_type`; аналогично `propagate_on_container_move_assignment` и `propagate_on_container_swap`; `swap` при `false` и неравных аллокаторах — UB.
См.: named_req/AllocatorAwareContainer, memory/allocator_traits

## cpp-c-0641 · cpp-t-083
Зачем контейнеру empty base optimization для аллокатора?
---
Размер любого объекта или члена не меньше 1, даже у пустого класса, а подобъект пустой базы может занимать 0 байт. Аллокатор без состояния (`std::allocator`) пуст, поэтому реализации хранят его как базу (с C++20 — `[[no_unique_address]]`), чтобы контейнер не рос [не по cppreference].
Подвох: EBO запрещена, если первый нестатический член имеет тот же пустой базовый тип.
См.: language/ebo

## cpp-c-0621 · cpp-t-084
Чем выражение `new T(args...)` отличается от вызова `operator new`?
---
Выражение `new` вызывает функцию выделения `operator new(sizeof(T))`, затем конструирует объект; `operator new` только выделяет сырую память. Парное `delete`-выражение вызывает деструктор, затем `operator delete`.
```cpp
struct S { S() {} ~S() {} };
void* p = ::operator new(sizeof(S)); // только память
S* s = new (p) S;                    // только конструктор
s->~S(); ::operator delete(p);
```
Подвох: `operator new` можно перегрузить, выражение `new` — нельзя.
См.: language/new, language/delete

## cpp-c-0622 · cpp-t-084
Что происходит с памятью, если конструктор объекта, созданного через `new`, бросает исключение?
---
Если инициализация завершилась исключением, ищется парная функция освобождения; если найдена, она вызывается для освобождения памяти, затем исключение продолжает распространяться. Деструктор самого объекта не вызывается.
Подвох: для placement-формы парной считается `operator delete` с теми же дополнительными параметрами; не нашлась — память не освобождается (возможна утечка).
См.: language/new

## cpp-c-0642 · cpp-t-084
Чем `new (std::nothrow) T` отличается от обычного `new`?
---
Обычный `new` при нехватке памяти бросает `std::bad_alloc`; `new (std::nothrow)` не бросает исключение и возвращает нулевой указатель, поэтому результат нужно проверять.
```cpp
std::size_t n = 1000000;
int* p = new (std::nothrow) int[n];
if (!p) { /* не хватило памяти */ }
```
Подвох: при нулевом указателе `new`-выражение завершается сразу и конструктор не вызывает.
См.: language/new, memory/new

## cpp-c-0643 · cpp-t-084
Что такое destroying delete и для чего он нужен?
---
С C++20 класс может объявить `void operator delete(T* p, std::destroying_delete_t)`. Тогда `delete`-выражение не вызывает деструктор само: уничтожение объекта и освобождение памяти — обязанность этой функции. Нужен, чтобы управлять уничтожением самостоятельно, например при базе без виртуального деструктора [не по cppreference].
Подвох: если среди найденных функций есть destroying delete, остальные игнорируются; удаление через базовый указатель без виртуального деструктора допустимо только с ним.
См.: language/delete, language/virtual

## cpp-c-0623 · cpp-t-085
Что означает выравнивание типа и как его запросить?
---
Выравнивание — требование к адресу объекта (кратность степени двойки). `alignof(T)` даёт его в байтах (`size_t`), `alignas(N)` задаёт требуемое выравнивание объявления.
```cpp
struct alignas(16) V { float x[4]; };
static_assert(alignof(V) == 16);
```
Подвох: `alignas` слабее естественного выравнивания — ошибка, `alignas(3)` недопустимо, `alignas(0)` игнорируется.
См.: language/alignas, language/alignof

## cpp-c-0624 · cpp-t-085
Что такое битовое поле?
---
Член класса с заданной шириной в битах: `unsigned flag : 1;`. Тип — целочисленный (включая `bool`) или перечисление; соседние поля обычно упаковываются в общие байты, но это определяется реализацией.
```cpp
struct Flags { unsigned a : 3; unsigned b : 5; };
Flags f{}; f.a = 7; // &f.a — ошибка
```
Подвох: нельзя взять адрес и неконстантную ссылку; значение, не влезающее в ширину, даёт результат, определяемый реализацией (обычно по модулю); безымянное поле шириной 0 начинает следующее с новой ячейки.
См.: language/bit_field

## cpp-c-0648 · cpp-t-085
Что такое `std::max_align_t` и как с выравниванием справляются `malloc` и `new`?
---
`std::max_align_t` — тип, чьё выравнивание не слабее, чем у любого скалярного типа. Указатели от `std::malloc` и подобных функций выделения выровнены не слабее `max_align_t`, поэтому годятся для любого обычного объекта.
Подвох: для типов со строже `__STDCPP_DEFAULT_NEW_ALIGNMENT__` выражение `new` передаёт выравнивание функции выделения как `std::align_val_t` (C++17); `malloc` такой гарантии не даёт.
См.: types/max_align_t, language/new

## cpp-c-0625 · cpp-t-086
Какую перегрузку `std::forward` применяют для lvalue и rvalue?
---
Обе перегрузки принимают `std::remove_reference_t<T>&` и `std::remove_reference_t<T>&&` соответственно и возвращают `static_cast<T&&>(x)`. `T` не выводится (невыводимый контекст) — его указывают явно: `std::forward<T>(x)`.
```cpp
template<class T> void wrap(T&& x) { g(std::forward<T>(x)); }
```
Подвох: при `T = U&` результат `U&` (lvalue), при `T = U` — `U&&`; вторая перегрузка с `T` — lvalue-ссылкой не компилируется.
См.: utility/forward

## cpp-c-0626 · cpp-t-086
Почему `std::forward` нельзя объявить только с параметром `T&` или только с `T&&`?
---
Внутри обёртки именованный `x` — lvalue, поэтому `forward<T>(x)` требует перегрузки, принимающей lvalue (`T&`); при единственной `T&&` она не связывается. А `forward<T>(f())` с rvalue-выражением требует `T&&`, который `T&` принять не может.
Подвох: имя `T&&` в параметре обёртки — forwarding reference только при выводе `T`; параметр `forward` не выводит `T` вовсе.
См.: utility/forward

## cpp-c-0627 · cpp-t-087
Как связаны категории glvalue, lvalue, xvalue и prvalue?
---
glvalue = lvalue ∪ xvalue (есть идентичность); rvalue = xvalue ∪ prvalue (можно перемещать). xvalue — «истекающий» объект: `std::move(x)`, вызов функции с `T&&`; prvalue — литерал, `a + b`, вызов функции с `T`.
```cpp
std::string s;
std::move(s);   // xvalue
std::string{};  // prvalue; в `std::string{}.size()` материализуется временный объект
```
Подвох: temporary materialization превращает prvalue в xvalue при привязке ссылки или обращении к члену.
См.: language/value_category

## cpp-c-0628 · cpp-t-087
Чем гарантированное устранение копирования отличается от NRVO?
---
С C++17 инициализация объекта prvalue того же типа (`return T(...)`, `T x = T(...)`) обязана строить объект сразу на месте: копирующий/перемещающий конструктор не нужен. NRVO (возврат именованного локального объекта) разрешено, но не обязательно.
```cpp
struct N { N() = default; N(N&&) = delete; };
N a() { return N(); }       // C++17: корректно
// N b() { N n; return n; } // ошибка: NRVO не гарантировано
```
Подвох: деструктор типа должен быть доступен и не удалён.
См.: language/copy_elision

## cpp-c-0629 · cpp-t-088
Когда срабатывает class template argument deduction (CTAD)?
---
С C++17 при объявлении переменной, `new` или функциональном приведении с именем шаблона класса без списка аргументов компилятор строит неявные deduction guides из конструкторов и копирующий кандидат и выбирает по разрешению перегрузки.
```cpp
std::pair p(1, 2.5);     // pair<int, double>
std::less l;             // less<void>
```
Подвох: для агрегатов вывод (aggregate deduction candidate) есть только с C++20; при наличии пользовательских guides агрегатный кандидат не добавляется.
См.: language/ctad

## cpp-c-0630 · cpp-t-088
Как задают пользовательское правило вывода аргументов CTAD?
---
Объявляют deduction guide в области видимости шаблона: `Имя(параметры) -> Специализация;`, без тела; он участвует в выводе вместе с неявными.
```cpp
template<class T> struct Box { Box(T, int); };
Box(const char*, int) -> Box<std::string>;
Box b("x", 1); // Box<std::string>
```
Подвох: guide — не функция: для него строится фиктивная функция (шаблон, если у guide есть параметры шаблона) с возвращаемым типом из `->`.
См.: language/deduction_guide, language/ctad

## cpp-c-0644 · cpp-t-088
Что компилятор проверяет до и после инстанцирования шаблона (двухфазная трансляция)?
---
Независимые от параметров шаблона имена ищутся и привязываются в точке определения; поиск зависимых имён откладывается до инстанцирования (обычный — по контексту определения, ADL — ещё и по контексту инстанцирования).
```cpp
void g(double);
template<class T> void f() { g(1); } // g независимое, привязано сейчас
void g(int);                          // f<int>() всё равно вызовет g(double)
```
Подвох: если смысл независимого имени между определением и инстанцированием меняется, программа некорректна без диагностики.
См.: language/dependent_name

## cpp-c-0645 · cpp-t-088
Что такое явное инстанцирование шаблона и зачем оно нужно?
---
`template class Foo<int>;` — явное определение инстанцирования: принудительно порождает класс (разрешено один раз на программу); `extern template class Foo<int>;` (C++11) подавляет неявное инстанцирование, код использует определение из другого места. Так сокращают время компиляции.
Подвох: для класса определение шаблона должно быть видно; без явного определения `extern template` даёт ошибки линковки; такое определение игнорирует спецификаторы доступа.
См.: language/class_template

## cpp-c-0631 · cpp-t-089
Как structured binding связывается с объектом-кортежем?
---
Если `std::tuple_size<E>` — полный тип с членом `value`, используется tuple-like протокол: число имён должно равняться `tuple_size`, значения берутся через `get<i>`, типы — через `tuple_element`. Остальные случаи: массив и класс с доступными нестатическими полями.
```cpp
std::tuple<int, std::string> t{1, "a"};
auto& [n, s] = t; // ссылки на элементы t
```
Подвох: `auto [a, b]` копирует объект, `auto& [a, b]` ссылается на него; число имён обязано совпасть.
См.: language/structured_binding

## cpp-c-0632 · cpp-t-089
Чем отличаются `std::make_tuple`, `std::tie` и `std::forward_as_tuple`?
---
`make_tuple` создаёт кортеж значений (`decay`; `reference_wrapper<X>` превращается в `X&`); `tie` — `tuple<T&...>` из lvalue (принимает и `std::ignore`); `forward_as_tuple` — `tuple<Types&&...>`: ссылки, rvalue-ссылки для rvalue.
```cpp
int a = 0; std::string b;
std::tie(a, b) = std::make_pair(1, std::string("x")); // присвоит a и b
```
Подвох: `forward_as_tuple` хранит ссылки — не сохранять кортеж дольше самих объектов.
См.: utility/tuple/make_tuple, utility/tuple/tie, utility/tuple/forward_as_tuple

## cpp-c-0646 · cpp-t-089
Для чего нужны `std::ignore` и `std::piecewise_construct`?
---
`std::ignore` — заполнитель для пропуска элемента при распаковке `tie`: `std::tie(a, std::ignore) = t;`. `std::piecewise_construct` — тег для конструктора `pair`: аргументы каждого члена передаются отдельным кортежем, и члены строятся из них напрямую.
```cpp
std::pair<std::string, std::string> p(std::piecewise_construct,
    std::forward_as_tuple("a"), std::forward_as_tuple(3, 'c')); // "a", "ccc"
```
Подвох: без тега каждый кортеж был бы целым элементом пары.
См.: utility/tuple/ignore, utility/piecewise_construct

## cpp-c-0633 · cpp-t-090
Как `std::weak_ptr` помогает разорвать цикл владения `shared_ptr`?
---
`weak_ptr` ссылается на объект, не увеличивая счётчик сильных владельцев. Если два объекта владеют друг другом через `shared_ptr`, счётчики не достигают нуля и происходит утечка; замена одной связи на `weak_ptr` разрывает цикл.
```cpp
struct B;
struct A { std::shared_ptr<B> b; };
struct B { std::weak_ptr<A> a; }; // shared_ptr здесь дал бы утечку
```
Подвох: `weak_ptr` не даёт доступа к объекту напрямую — только через `lock()`.
См.: memory/weak_ptr

## cpp-c-0634 · cpp-t-090
Как безопасно получить `shared_ptr` из `weak_ptr`?
---
`wp.lock()` эквивалентно `expired() ? shared_ptr<T>() : shared_ptr<T>(*this)`, но выполняется атомарно: результат — владеющий `shared_ptr` или пустой, если объекта уже нет.
```cpp
if (auto sp = wp.lock()) { sp->f(); } // sp держит объект до конца блока
```
Подвох: при общем доступе из потоков `expired()` осмыслен, только когда вернул `true`; конструктор `shared_ptr(wp)` для пустого `wp` бросает `bad_weak_ptr`.
См.: memory/weak_ptr/lock, memory/weak_ptr

## cpp-c-0647 · cpp-t-090
Что хранится в блоке управления, чтобы `weak_ptr` работал?
---
Блок управления держит два счётчика: сильный (число `shared_ptr`) и слабый (число `weak_ptr`). Объект уничтожается, когда сильный счётчик нулевой; сам блок освобождается, когда равен нулю и слабый. `lock()` увеличивает сильный счётчик только если он ненулевой [не по cppreference].
Подвох: при `make_shared` объект и блок в одной аллокации — память освобождается лишь после обнуления слабого счётчика.
См.: memory/weak_ptr, memory/shared_ptr

## cpp-q-601
ticket: cpp-t-064 · level: L0
Что возвращает `decltype(x)` для объявленной переменной `x`, и как `decltype(auto)` выводит тип?
### Эталон
- Если аргумент `decltype` — id-выражение без скобок, обозначающее переменную, результатом является объявленный тип этой переменной.
- Для иных выражений `decltype(e)` учитывает категорию значения: lvalue даёт `T&`, xvalue — `T&&`, prvalue — `T`.
- `decltype(auto)` выводит тип по правилам `decltype` из инициализатора; скобки могут изменить результат: для `int x;` `decltype(x)` — `int`, а `decltype((x))` — `int&`.
- Например, `int& x = ...; decltype(auto) by_name() { return x; }` возвращает `int`, а `decltype(auto) by_expr() { return (x); }` возвращает `int&`: неконструкция-id даёт объявленный тип, а скобки превращают выражение в lvalue.

## cpp-q-602
ticket: cpp-t-064 · level: L1
Каковы типы `a`, `b` и `c` в примере? Почему `decltype(auto)` в `b` и `c` даёт разные результаты?
```cpp
int x = 1;
decltype(auto) a = x;
decltype(auto) b = (x);
decltype(auto) c = x + 1;
```
### Эталон
- `a` имеет тип `int`: неконструкция-id `x` в `decltype(x)` даёт объявленный тип переменной.
- `b` имеет тип `int&`: `(x)` — lvalue-выражение.
- `c` имеет тип `int`: `x + 1` — prvalue.
- Присваивание через `b` изменяет `x`; `a` и `c` — отдельные объекты.

## cpp-q-603
ticket: cpp-t-065 · level: L0
Что возвращает `std::move_if_noexcept(x)` и как выбирается тип результата?
### Эталон
- Функция возвращает `const T&`, если перемещение может бросить исключение и `T` копируем; иначе возвращает `T&&`.
- Условие выбора `const T&`: `!is_nothrow_move_constructible_v<T> && is_copy_constructible_v<T>`.
- Это средство выбора безопасной операции переноса или копирования, а не само перемещение объекта.

## cpp-q-604
ticket: cpp-t-065 · level: L1
Почему при реаллокации вектора выбор копирования через `move_if_noexcept` может сохранить гарантию исключений? Почему нельзя всегда использовать `memcpy`?
### Эталон
- Если перемещение потенциально бросает, а копирование доступно, копирование оставляет старые элементы неизменными до успешного построения новых; при исключении новый буфер можно уничтожить.
- Если перемещение `noexcept` или копирование недоступно, используют перемещение; для некопируемого типа с бросающим перемещением сильная гарантия может быть утрачена.
- `memcpy` побайтно копирует представление и не вызывает конструкторы; это не является корректным копированием произвольных объектов C++.
- Для trivially copyable типа байты его представления можно скопировать в массив `char`, `unsigned char` или `std::byte`, а затем скопировать обратно в тот же объект, восстановив исходное значение. Это узкое правило работы с представлением не делает `memcpy` заменой корректного копирования произвольных объектов: оно не запускает конструкторы и не переносит владение ресурсами.

## cpp-q-605
ticket: cpp-t-066 · level: L0
Сравните владение и копируемость `std::unique_ptr<T>` и `std::shared_ptr<T>`.
### Эталон
- `unique_ptr` выражает единоличное владение; он перемещаемый, но некопируемый.
- `shared_ptr` выражает совместное владение; его копии разделяют объект и совместно учитываются счётчиком владельцев.
- При уничтожении последнего владеющего `shared_ptr` управляемый объект удаляется.
- `weak_ptr` может наблюдать объект под управлением `shared_ptr`, не увеличивая число владеющих ссылок.

## cpp-q-606
ticket: cpp-t-066 · level: L1
Какой вывод даст пример? Что обеспечивает удаление объекта при копировании `shared_ptr`?
```cpp
#include <iostream>
#include <memory>
int main() {
    auto p = std::make_shared<int>(7);
    {
        auto q = p;
        std::cout << p.use_count() << ' ';
    }
    std::cout << p.use_count() << ' ' << *p;
}
```
### Эталон
- Вывод: `2 1 7`.
- Копирование `q = p` создаёт второго совместного владельца; выход из внутренней области уничтожает `q`, поэтому счётчик снова равен 1.
- Управляемый `int` уничтожается, когда счётчик совместных владельцев достигает нуля.
- Счётчик совместных владельцев не означает, что сам объект `int` является потокобезопасным.

## cpp-q-607
ticket: cpp-t-067 · level: L0
Что такое замыкание лямбда-выражения, и что меняет спецификатор `mutable`?
### Эталон
- Лямбда-выражение создаёт объект замыкания с типом, заданным реализацией; захваченные значения хранятся в его состоянии.
- Без `mutable` оператор вызова лямбды с захватом по значению имеет `const`-квалификацию, поэтому копии захваченных объектов нельзя изменять внутри вызова.
- `mutable` снимает эту `const`-квалификацию и позволяет менять захваченные копии; исходные объекты при этом не меняются.

## cpp-q-608
ticket: cpp-t-067 · level: L1
Что выведет программа? Почему `n` снаружи лямбды не изменится?
```cpp
#include <iostream>
int main() {
    int n = 2;
    auto f = [n]() mutable { return ++n; };
    std::cout << f() << ' ' << n;
}
```
### Эталон
- Вывод: `3 2`.
- Захват `[n]` сохраняет в замыкании копию `n`.
- `mutable` позволяет изменить хранимую копию; исходная переменная остаётся равной 2.
- Повторный вызов того же объекта замыкания увеличил бы его сохранённую копию ещё раз.

## cpp-q-609
ticket: cpp-t-068 · level: L0
Что означает SFINAE и какую роль играет `std::enable_if`?
### Эталон
- SFINAE означает, что ошибка подстановки типа или выражения в непосредственном контексте шаблонной специализации приводит к исключению кандидата из перегрузки, а не к общей ошибке компиляции.
- `std::enable_if<B, T>::type` существует при истинном `B`; при ложном условии такого вложенного типа нет.
- `enable_if` позволяет условно сделать шаблонную перегрузку допустимым кандидатом.

## cpp-q-610
ticket: cpp-t-068 · level: L1
Для каких типов допустим вызов `f` в C++20? Как SFINAE исключает неподходящую перегрузку?
```cpp
#include <type_traits>
template<class T, std::enable_if_t<std::is_integral_v<T>, int> = 0>
int f(T) { return 1; }
int main() { return f(3); }
```
### Эталон
- Вызов `f(3)` допустим: выводится `T = int`, условие `is_integral_v<int>` истинно.
- Для аргумента типа `double` подстановка дала бы `enable_if_t<false, int>`, что не имеет типа `type`; эта шаблонная перегрузка исключается из набора кандидатов.
- Если других подходящих перегрузок нет, вызов с `double` не компилируется.

## cpp-q-611
ticket: cpp-t-069 · level: L0
Что делает ограничение `requires` в C++20 и чем является выражение `requires { ... }`?
### Эталон
- Ограничение `requires` проверяет требования к шаблонным параметрам и допускает шаблон или функцию к использованию, когда требования выполнены.
- Выражение `requires { ... }` — compile-time булево выражение, проверяющее корректность перечисленных требований в данном контексте.
- Требования в выражении могут быть простыми, составными, типовыми и вложенными.
- Ограничение можно записать полной формой `template<class T> requires std::integral<T> void f(T);` или сокращённо: `template<std::integral T> void f(T);` (нужен `<concepts>`).
- Пример составного requirement: `template<class T> concept HasSize = requires(T x) { { x.size() } -> std::convertible_to<std::size_t>; };` проверяет корректность `x.size()` и совместимость результата с `std::size_t` (нужны `<concepts>` и `<cstddef>`).

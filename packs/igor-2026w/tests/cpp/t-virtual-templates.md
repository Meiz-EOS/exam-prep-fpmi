## cpp-q-701
ticket: cpp-t-076 · level: L0
Что гарантирует виртуальный вызов в конструкторе или деструкторе и какие ограничения относятся к pure virtual функциям и шаблонным виртуальным методам?
### Эталон
- При вызове виртуальной функции из конструктора/деструктора диспетчеризация ограничена текущим классом: переопределение в более производном классе не вызывается.
- Вызов чисто виртуальной функции прямо или косвенно из конструктора/деструктора класса, где она объявлена чистой, приводит к неопределённому поведению; чисто виртуальная функция может иметь определение.
- Виртуальная функция не может быть шаблоном функции.
- Аргументы по умолчанию выбираются статически по типу выражения, а тело виртуальной функции — динамически по типу объекта.

## cpp-q-702
ticket: cpp-t-076 · level: L1
Что выведет программа? Объясните различие между выбором виртуальной функции и аргумента по умолчанию.
```cpp
struct B { virtual int f(int x = 1) { return x; } };
struct D : B { int f(int x = 2) override { return x; } };
int main() { D d; B& b = d; std::cout << b.f(); }
```
### Эталон
- Будет выведено `1`.
- Статический тип выражения `b` — `B&`, поэтому берётся аргумент по умолчанию `B::f`.
- Динамический тип объекта — `D`, поэтому вызывается тело `D::f(1)`.

## cpp-q-703
ticket: cpp-t-077 · level: L0
Как объявить параметр шаблона, который сам является шаблоном класса, и почему allocator обычно передают не таким параметром?
### Эталон
- Параметр шаблона-шаблона объявляют, например, `template<template<class...> class C>`. В C++20 ключевое слово `typename` также допустимо вместо `class`.
- Контейнерный шаблон может иметь дополнительные параметры, например аллокатор; шаблон шаблона должен быть совместим с арностью и параметрами шаблона аргумента.
- `std::allocator_traits<Alloc>` принимает тип аллокатора `Alloc`, а через `rebind_alloc<U>` получает аллокатор для другого типа элемента; сам `Alloc` поэтому является параметром-типа, а не шаблонным параметром-шаблоном.

## cpp-q-704
ticket: cpp-t-077 · level: L1
В шаблоне `template<class T> struct D : Base<T> { void f() { value = 1; } };` почему `value` может не найтись? Покажите корректную запись для члена базового шаблона и зависимого вложенного шаблона `rebind`.
### Эталон
- `Base<T>` — зависимая база; неквалифицированный поиск имени `value` не ищет в ней при разборе определения `D`.
- Обращение можно записать как `this->value = 1;` или `Base<T>::value = 1;`.
- Для зависимого вложенного шаблона нужна форма `typename A::template rebind<U>::other`: `template` сообщает, что `rebind` — шаблон, а `typename` — что итоговое зависимое имя является типом.

## cpp-q-705
ticket: cpp-t-078 · level: L0
Запишите четыре формы fold-expression и назовите нейтральные значения унарных свёрток для пустого пакета.
### Эталон
- Унарные формы: `(pack op ...)` и `(... op pack)`.
- Бинарные формы: `(pack op ... op init)` и `(init op ... op pack)`.
- Для пустого пакета определены унарные свёртки с `&&` (значение `true`), `||` (значение `false`) и `,` (значение `void()`); остальные операторы требуют непустого пакета.

## cpp-q-706
ticket: cpp-t-078 · level: L1
Что выведет программа? Укажите порядок вывода и почему скобки важны.
```cpp
template<class... T> void print(T const&... xs) { ((std::cout << xs << ' '), ...); }
int main() { print(1, 2, 3); }
```
### Эталон
- Вывод: `1 2 3 ` (после последнего пробела — перевод строки не добавляется).
- Это унарная правая свёртка по оператору запятая: `((std::cout << xs << ' '), ...)`.
- Оператор запятая вычисляет выражения слева направо, поэтому значения печатаются в порядке аргументов.

## cpp-q-707
ticket: cpp-t-079 · level: L0
Чем отличаются `std::back_inserter` и `std::inserter`, и что делают потоковые итераторы ввода и вывода?
### Эталон
- `std::back_inserter(c)` создаёт выходной итератор, присваивание которому добавляет элемент через `c.push_back`.
- `std::inserter(c, pos)` создаёт выходной итератор, который вставляет элемент перед текущей позицией и продвигает позицию за вставленный элемент.
- `std::istream_iterator<T>` читает значения типа `T` из потока; `std::ostream_iterator<T>` записывает присваиваемые значения в поток, при необходимости добавляя разделитель.

## cpp-q-708
ticket: cpp-t-079 · level: L1
Какой контейнерный член требуется для `std::back_inserter`, и почему этот алгоритм не подходит для `std::set`?
```cpp
std::set<int> s;
std::copy(v.begin(), v.end(), std::back_inserter(s));
```
### Эталон
- Код некорректен: `std::set` не предоставляет `push_back`.
- `back_insert_iterator` выполняет присваивание через `container.push_back(value)`; это подходит, например, для `std::vector` и `std::list`.
- Для вставки в ассоциативный контейнер можно применять `std::inserter(s, s.end())`.

## cpp-q-709
ticket: cpp-t-080 · level: L0
Какие гарантии инвалидирования итераторов, указателей и ссылок у `std::unordered_map` при rehash и удалении элемента?
### Эталон
- Rehash инвалидирует итераторы контейнера, но не инвалидирует указатели и ссылки на элементы.
- Удаление элемента инвалидирует итераторы, указатели и ссылки только на удалённый элемент.
- Вставка инвалидирует итераторы, если она вызывает rehash; без rehash итераторы остаются действительными.

## cpp-q-710
ticket: cpp-t-080 · level: L1
Почему реализация `unordered_map` как вектора списков неудобна для обычного сквозного итератора? Назовите роль `load_factor` и `rehash`.
### Эталон
- В итераторе по всем элементам после конца текущего списка пришлось бы искать следующий непустой бакет; при разреженном массиве бакетов это может сделать продвижение дорогим.
- Один возможный вариант реализации — связать непустые узлы в глобальную цепь для сквозного обхода, храня отдельно принадлежность бакетам и/или хеши узлов; стандарт не предписывает такое устройство.
- `load_factor` — среднее число элементов на бакет; `rehash(n)` перестраивает бакеты с числом не меньше заданного и может инвалидировать итераторы.

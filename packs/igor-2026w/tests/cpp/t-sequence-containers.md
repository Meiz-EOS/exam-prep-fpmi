## cpp-q-508
ticket: cpp-t-055 · level: L0
Назовите основные характеристики `std::vector`: что означают `size` и `capacity`, и что гарантирует `reserve`?
### Эталон
- `std::vector` — последовательный контейнер с непрерывно хранящимися элементами.
- `size()` — число элементов; `capacity()` — число элементов, которое может храниться без реаллокации.
- `reserve(n)` при `n > capacity()` запрашивает ёмкость не меньше `n`; он не меняет `size()`.
- Реаллокация инвалидирует все итераторы, указатели и ссылки на элементы, включая старый `end()`.
- `operator[]` не проверяет границы; `at()` проверяет и выбрасывает `std::out_of_range`, если индекс вне диапазона.
- `vector<bool>` — специализированная реализация, которая может упаковывать биты; её `reference` может быть прокси-объектом, а `data()` и обычные `bool&`-ссылки не обеспечиваются.

## cpp-q-509
ticket: cpp-t-055 · level: L1
Что выведет программа? Какой итератор инвалидируется при `push_back`, если реаллокации нет?
```cpp
#include <iostream>
#include <vector>
int main() {
    std::vector<int> v;
    v.reserve(3);
    v.push_back(7);
    auto it = v.begin();
    auto old_end = v.end();
    v.push_back(v[0]);
    std::cout << *it << ' ' << v.size();
    (void)old_end;
}
```
### Эталон
- Вывод: `7 2`.
- `reserve(3)` обеспечивает ёмкость не меньше 3, поэтому добавление второго элемента не требует реаллокации.
- При `push_back` без реаллокации итераторы и ссылки на существующие элементы остаются действительными, но прежний `end()` инвалидируется.
- `v[0]` используется до изменения размера и даёт элемент со значением `7`.

## cpp-q-510
ticket: cpp-t-056 · level: L0
Чем `std::deque` отличается от `std::vector` по устройству и доступным операциям?
### Эталон
- `std::deque` предоставляет произвольный доступ и эффективные вставку/удаление на обоих концах; `std::vector` эффективен при добавлении в конец.
- В отличие от `std::vector`, элементы `std::deque` не обязаны занимать один непрерывный блок памяти.
- У `std::deque` есть `push_front`/`pop_front`; у `std::vector` этих операций-членов нет.
- `std::vector` предоставляет `data()` и гарантирует непрерывное хранение; такая гарантия не дана для `std::deque`.

## cpp-q-511
ticket: cpp-t-056 · level: L1
После вставки элемента в начало `std::deque` какие гарантии остаются у указателей и ссылок на прежние элементы, а какие у итераторов?
```cpp
#include <deque>
int main() {
    std::deque<int> d{1, 2, 3};
    int* p = &d[1];
    auto it = d.begin() + 1;
    d.push_front(0);
    // Какие из p и it можно использовать?
}
```
### Эталон
- После вставки на любой конец deque все итераторы инвалидируются.
- Вставка на конец deque не инвалидирует ссылки на существующие элементы; вставка в начало также сохраняет ссылки на прежние элементы.
- Поэтому `p` остаётся указателем на прежний элемент `2`, но использовать `it` после `push_front` нельзя.
- Это правило для `deque`; оно отличается от правила `vector`, у которого добавление без реаллокации сохраняет итераторы на прежние элементы.

## cpp-q-512
ticket: cpp-t-057 · level: L0
Как устроен `std::list` на уровне модели и какие свойства имеют его итераторы при вставке и удалении?
### Эталон
- `std::list` — двусвязный последовательный контейнер; стандарт не предписывает конкретное внутреннее представление узлов.
- Вставка элемента не инвалидирует итераторы и ссылки на уже существующие элементы.
- Удаление элемента инвалидирует итераторы и ссылки только на удалённый элемент.
- `splice`, `sort`, `merge` и `reverse` — операции, предоставляемые `std::list`; `sort` и `merge` сохраняют итераторы и ссылки на элементы.

## cpp-q-513
ticket: cpp-t-057 · level: L1
Что напечатает программа и остаётся ли `it` действительным?
```cpp
#include <iostream>
#include <list>
int main() {
    std::list<int> xs{1, 2, 3};
    auto it = ++xs.begin();
    xs.push_front(0);
    xs.erase(xs.begin());
    std::cout << *it;
}
```
### Эталон
- Вывод: `2`.
- `it` указывает на элемент `2`.
- Вставка в `list` сохраняет итераторы к существующим элементам; `erase` инвалидирует только итераторы к удалённому элементу (здесь это `0`).
- `splice` переносит элементы списка без копирования их значений; для разных списков их аллокаторы должны сравниваться равными.
- `std::forward_list` — односвязный вариант списка с операциями, ориентированными на позицию «после»; у него нет `size()`.

## cpp-q-514
ticket: cpp-t-058 · level: L0
Что хранит элемент `std::map<Key, T>` и как соотносятся `std::pair`, `std::make_pair` и тип значения карты?
### Эталон
- `std::map<Key, T>` содержит пары «ключ–значение»; тип элемента — `std::pair<const Key, T>`.
- Ключ в элементе карты `const`, чтобы изменение ключа не нарушало упорядочение.
- В C++20 `std::make_pair(a, b)` возвращает `std::pair` с элементами типа `unwrap_ref_decay_t<decltype(a)>` и `unwrap_ref_decay_t<decltype(b)>`; в частности, `std::reference_wrapper<T>` разворачивается в `T&`.
- Стандарт гарантирует упорядоченное ассоциативное поведение, но не требует реализации `std::map` именно красно-чёрным деревом.

## cpp-q-515
ticket: cpp-t-058 · level: L1
Что выведет программа? Почему ключ нельзя изменить через итератор карты?
```cpp
#include <iostream>
#include <map>
int main() {
    std::map<int, int> m{{2, 20}};
    auto it = m.begin();
    it->second = 21;
    std::cout << it->first << ' ' << it->second;
    // it->first = 3; // допустимо ли?
}
```
### Эталон
- Вывод: `2 21`.
- `it->second` имеет тип `int&`, поэтому mapped value можно менять.
- `it->first` имеет тип `const int&`, так как элемент карты имеет тип `std::pair<const int, int>`; присваивание ключу не компилируется.
- Для поиска/вставки/удаления карта использует свой порядок ключей, задаваемый компаратором; стандарт не фиксирует конкретную структуру дерева.

## cpp-q-516
ticket: cpp-t-059 · level: L0
Что такое `std::string_view` и чем он отличается от `std::string`?
### Эталон
- `std::string_view` — невладеющее представление непрерывной последовательности символов с длиной.
- Он позволяет передавать/срезать представления без копирования символов.
- `std::string` владеет своей строкой и управляет её хранилищем; `string_view` этого не делает.
- Представление допустимо использовать, только пока живы символы, на которые оно ссылается; изменение или уничтожение владельца может сделать view некорректным.

## cpp-q-612
ticket: cpp-t-070 · level: L0
Для чего предназначены `std::function` и `std::bind`?
### Эталон
- `std::function<R(Args...)>` — копируемая type-erasure обёртка для вызываемого объекта, совместимого с сигнатурой `R(Args...)`.
- `std::bind` создаёт вызываемый объект, хранящий целевую функцию и заданные аргументы; плейсхолдеры задают позиции аргументов, передаваемых при вызове.
- Для обёртки вызова с привязкой аргументов часто можно использовать лямбду; `std::function` может иметь дополнительные затраты на хранение и косвенный вызов.

## cpp-q-613
ticket: cpp-t-070 · level: L1
Что напечатает код? Как `std::bind` связывает аргумент с плейсхолдером?
```cpp
#include <functional>
#include <iostream>
int sub(int a, int b) { return a - b; }
int main() {
    auto f = std::bind(sub, std::placeholders::_1, 2);
    std::function<int(int)> g = f;
    std::cout << g(7);
}
```
### Эталон
- Вывод: `5`.
- При вызове `g(7)` значение `7` подставляется вместо `_1`, а второй аргумент `sub` заранее связан со значением `2`.
- `std::function<int(int)>` принимает этот объект, поскольку он вызывается с одним `int` и результат совместим с `int`.

## cpp-q-614
ticket: cpp-t-071 · level: L0
Как читать сложное объявление C++ и где группировать его части?
### Эталон
- Чтение начинается от имени объявляемого объекта: скобки вокруг имени и указателей/ссылок задают связывание раньше окружающих массивов и функций.
- Операторы `[]` и `()` связываются с именем сильнее, чем `*` и `&`; скобки меняют это связывание.
- Декларацию можно проверять по частям, заменив имя на выражение: например, `int *a[3]` — массив из трёх указателей на `int`, а `int (*a)[3]` — указатель на массив из трёх `int`.

## cpp-q-615
ticket: cpp-t-071 · level: L1
Каковы типы `a` и `b`? Назовите отличие между объявлениями.
```cpp
int *a[3];
int (*b)[3];
```
### Эталон
- `a` — массив из трёх указателей на `int`.
- `b` — указатель на массив из трёх элементов типа `int`.
- В первом объявлении `[]` связывается с именем раньше `*`; во втором скобки связывают `*b` перед `[]`.

## cpp-q-616
ticket: cpp-t-072 · level: L0
Как объявляют указатели на поле и на метод класса, и как обращаются через них к объекту?
### Эталон
- Указатель на поле типа `T` класса `C` записывается как `T C::* p`; указатель на метод — как `R (C::*p)(Args...)` с нужными cv/ref-квалификаторами.
- Для объекта `obj` используют `(obj.*p)`, для указателя `ptr` — `(ptr->*p)`.
- Указатель на метод можно хранить в `std::function`: `struct C { int get() const; }; std::function<int(const C&)> f = &C::get;` — вызов `f(c)` применяет указатель на метод к объекту `c`.
- Указатель на член не обязан представляться обычным машинным адресом; его размер не гарантированно равен размеру обычного указателя.

## cpp-q-617
ticket: cpp-t-072 · level: L1
Что выведет программа? Как оператор `.*` применяет указатель на поле?
```cpp
#include <iostream>
struct S { int value; };
int main() {
    int S::* p = &S::value;
    S s{4};
    s.*p = 9;
    std::cout << s.value;
}
```
### Эталон
- Вывод: `9`.
- `int S::*` — указатель на поле типа `int` в классе `S`.
- Выражение `s.*p` обозначает соответствующее поле объекта `s`, поэтому присваивание меняет `s.value`.

## cpp-q-618
ticket: cpp-t-073 · level: L0
Как защищённое наследование меняет доступ к открытым и защищённым членам базового класса?
### Эталон
- При `class D : protected B` открытые и защищённые члены `B` доступны в `D` как защищённые члены `D`.
- Закрытые члены `B` не становятся доступными в `D`.
- Внешний код не может обращаться к унаследованным открытым членам `B` через объект `D`, поскольку они стали защищёнными.
- Дружественность не наследуется: друг базового класса не становится автоматически другом производного класса, и наоборот.
- Например, `struct A { protected: int x; }; struct B : public A {}; struct C : protected B { int f() { return x; } };`: `C::f` вправе обращаться к защищённому члену прародителя `A` через промежуточный `B`. Член остаётся доступен внутри цепочки наследования, но публичные члены `B` становятся защищёнными в `C`, так что внешний код не может использовать их через объект `C`.

## cpp-q-619
ticket: cpp-t-073 · level: L1
Скомпилируется ли `d.f()`? Почему вызов из `D::g` допустим?
```cpp
struct B { public: void f() {} };
struct D : protected B { void g() { f(); } };
int main() { D d; d.f(); }
```
### Эталон
- Определение `D::g` корректно: `f` доступна в производном классе и унаследована с защищённым доступом.
- Выражение `d.f()` в `main` некорректно: `f` является защищённым членом `D`.
- Защищённое наследование меняет доступ к публичному члену базы для внешних пользователей `D`, но не запрещает его использование внутри `D`.

## cpp-q-620
ticket: cpp-t-074 · level: L0
Как виртуальное наследование решает ромбовидное наследование и кто инициализирует виртуальную базу?
### Эталон
- Если обе ветви ромба виртуально наследуют одну базу, конечный наиболее производный объект содержит один подобъект этой виртуальной базы.
- Виртуальную базу инициализирует конструктор наиболее производного класса; инициализаторы этой базы в промежуточных классах при создании наиболее производного объекта не определяют её начальную инициализацию.
- При обычном невиртуальном наследовании каждая ветвь могла бы добавить собственный подобъект общей базы.

## cpp-q-621
ticket: cpp-t-074 · level: L1
Скомпилируется ли код и сколько раз вызывается конструктор `A` при создании `D`?
```cpp
struct A { A(int) {} };
struct B : virtual A { B() : A(1) {} };
struct C : virtual A { C() : A(2) {} };
struct D : B, C { D() : A(3), B(), C() {} };
int main() { D d; }
```
### Эталон
- Код компилируется; конструктор виртуальной базы `A` вызывается один раз при создании `D`.
- Инициализатор `A(3)` в `D` задаёт значение для единственного виртуального подобъекта `A`.
- Инициализаторы `A(1)` и `A(2)` в `B` и `C` игнорируются при создании `D`; они применялись бы, если бы `B` или `C` были наиболее производным объектом.

## cpp-q-622
ticket: cpp-t-075 · level: L0
Гарантирует ли стандарт C++ конкретное размещение базовых подобъектов, `vptr` и таблиц виртуальных функций?
### Эталон
- Стандарт задаёт семантику наследования, виртуальных вызовов и RTTI, но не фиксирует конкретную схему размещения полиморфного объекта в памяти.
- Имена `vptr`, `vtable` и смещения до верхнего объекта описывают распространённые ABI-механизмы, а не обязательные сущности модели C++.
- Поэтому число и расположение таких указателей, структура таблиц и хранение `type_info` зависят от реализации и ABI.
- Типичная схема ABI для ромба с виртуальной базой содержит один подобъект общей виртуальной базы, а производные подобъекты могут хранить метаданные или смещения для доступа к ней; полиморфные подобъекты часто содержат `vptr`, указывающий на таблицу виртуальных функций. Это лишь характерная модель реализации: стандарт не требует именно такой схемы, числа `vptr` или их расположения.

## cpp-q-623
ticket: cpp-t-075 · level: L1
Почему нельзя вывести переносимую раскладку памяти `D` только из этого кода? Какие объекты базовых классов гарантированно существуют в `D`?
```cpp
struct A { virtual ~A() = default; };
struct B : virtual A {};
struct C : virtual A {};
struct D : B, C {};
```
### Эталон
- Объект `D` содержит по одному подобъекту базовых классов `B`, `C` и один общий виртуальный подобъект `A`.
- Стандарт не устанавливает байтовые смещения этих подобъектов или число внутренних указателей реализации виртуальных вызовов.
- Конкретная раскладка полиморфного объекта и представление виртуальной базы зависят от реализации и ABI.
